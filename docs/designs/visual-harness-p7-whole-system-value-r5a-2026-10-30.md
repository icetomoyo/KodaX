# P7 执行修复补充 r5a：恢复生产辅助请求语义

2026-10-30。继承已批准的 [r5](visual-harness-p7-whole-system-value-r5-2026-10-30.md) 六格目标、题目、媒体、真值、两个提交及全部额度。不追加预算、不改题、不改生产实现。

## 新复现与修复

r5 L1 的第三请求是生产 `report_stall_judgment`，不是主任务请求。生产停滞检查允许自身约五秒截止后返回“不干预”；评估传输与 Runtime 包装却都把它的取消升级为主任务停止。之前八条原 fixture 回放未触发此并行旁路，未覆盖这个缺陷。

另查实：旧传输将所有请求 `max_tokens` 改为 Host 上限 8192，抬高了生产停滞判断的 1024 和后台记忆复盘的 1200。应使用生产合法上限与 Host 上限的较小值；未知 usage 的预留也必须以实际发送上限为准。

补修以真实 Runtime 重复读取触发停滞检查的联合回归先复现失败，再验证主任务正常交付。仅明确的停滞旁路 AbortError/TimeoutError可恢复：保持原生产默认判断、不取消主任务，仍记录原始失败和实际/预留成本。若旁路在串行队列中已经取消，记录未派发，物理调用与 token 均不增加。主请求、未知旁路、钱包/计量错误、全局预算限制仍按原停止规则处理。不能把这种生产旁路容错当作自动重试。

## 最小补跑与比较边界

r5 L1 保留为 `eval-invalid`。r5 L2 已正常交付两个真实缺陷，主任务配置未变，后台也完成，故先复用，不为形式整齐重烧整格。独立 Spec 评审同意这个最小补跑范围。

但 L2 后台发送上限为 8192、生产上限为1200，实际输出750。没有达到原上限不证明配置对生成无影响。L 配对必须标为**混合执行修订的探索性比较**，分别列前台和后台实际成本，不能将总差值全部归因于融合；更不能单独重放后台后拼接成虚构的端到端成本。如果最终决定依赖这一细小差异，才考虑另行统一配置补样本。

r5a 只发起受影响的 L1 与原来未执行的 H、V 四格，共五格。H/V 两版本使用相同补修配置；每格一次，无自动重试。生产提示、题目和公共媒体与 r5 完全一致。

r5 已发生11次请求，10次最终结算共184,587 token，另一次预留11,200 token（不是 actual）；元数据22次。由已批准的新增100次/2M额度中扣除后，r5a 剩余 **89次、1,804,213 token、196次metadata**。账户预检沿用同一实验快照，每次生成前后仍重新观察。费用停止线扣除此前观察增量，不重置已发生费用。旧 ledger 和 raw 不修改。
