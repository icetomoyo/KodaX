# P7：先看任务效果，再看全程 token 的验证方案

2026-10-29。**方案已写，尚未构建/冻结本方案的实验输入，尚未执行新模型调用。** 工程候选为 `3b2d48e8`（后续 `322ae5c4` 仅新增旧 pilot/记录），主比较基线为视觉改造前、已包含既有 token 优化的 `1826cc228f299995fe5b22e608c7fbd90c3dc9ee`。依照 [EVAL_GUIDELINES](../../benchmark/EVAL_GUIDELINES.md) 做有界受控任务，不启动自由展开的长 Agent loop。

## 1. 这次要回答的决定

用户最新要求优先于此前临时门槛：**先看实际任务是否做得更好，再看完整任务 token，最后决定处理方向。** 不预先把零增量、+10% 或 +20% 锁成采用条件。实验调用/费用预算仍是硬停止条件，和采用价值门槛是两回事。

先分别回答三项，再由 owner 决定保留、精简、按需装配或撤回：

1. 最终答案、补丁或环境终态是否改善？是否出现新的错误、幻觉、无效动作？
2. 达到这个结果总共用了多少输入/输出/推理 token、图片、工具调用和时间？多取证有没有减少错误尝试，还是只是增加步骤？
3. 收益发生在哪类任务？普通任务是否持续支付无收益的固定开销？不要用少数视觉题的胜利代表日常工作负载。

旧 [r3](visual-harness-p7-pilot-r3-2026-10-29.md) 的 alpha/算术四次调用只证明该路由能产出工具提案并测得单轮 usage。它没有执行取证，也没有比较取证后的任务结果。**其“更直接的选择”不作为任务效果提升的验收证据；+327/+619 也不作为完整任务成本。** 原 raw、计数、失败和限定结论保留，不重新生成以改变旧结论。

## 2. 为什么选这些场景

VISTA 的主体是保存原始视觉观察，允许模型主动重看局部/旧帧，再依据返回的真实证据继续推理和行动；并非单纯暴露一个像素工具。[论文 v1 §3.1–3.2](https://arxiv.org/html/2610.02200v1#S3)

论文静态任务含迷宫/连线追踪，交互任务需要根据反馈更新理解；因此可以验证最终结果，而不只计工具选择。[论文 §5、Fig.14](https://arxiv.org/html/2610.02200v1#S5)。论文部分消融同时改变自动送入的帧数，不能把成本变化全部归于记忆/检查；本方案两 arm 的初始图和自动送图政策保持一致。[论文 §4.3、App.A.2](https://arxiv.org/html/2610.02200v1#S4.SS3)

以下是迁移到 KodaX 的小任务，不是复现论文整套长程成绩。原论文的较长轨迹不能硬塞成三轮后把截断当成框架失败；选题前必须证明这里的小目标在预定边界内可完成。

## 3. 比较谁，防止原 token 优化被掩盖

| 比较 | 用途 | 本次地位 |
| --- | --- | --- |
| B0：`1826cc22`，已做 token 优化、未加视觉框架；C：`3b2d48e8` | 回答整套视觉改造对已有优化版本的任务效果/全程成本影响 | **主比较** |
| B1：`30310e00`，已含 P0–P2；C：`3b2d48e8` | 定位后续多 view/像素/时效等增量 | 只有主比较出现需要解释的差异才另开小批，不默认变三组烧预算 |

从各自真实版本生成生产 prompt、tools、图像及工具结果，使用相同模型/路由/推理设置、公共任务工作面和环境。**不把新版简单删几个工具冒充旧版，也不撤回旧版已有 token 优化。** 不重新跑整轮历史优化；只核对优化合同源/hash 及受影响的实际请求。

执行前离线证明 B0/C 都能收到相同原图和正常任务反馈。兼容问题先判配对推理实验未就绪，不能把“旧版没有收到图片”算成推理收益；真实来源支持的差异可单列工程能力事实。若历史接口需适配，只允许透明的入口/传输适配，保存 diff/hash 并证明不改变模型可见含义；不能给旧版补上新记忆、裁剪或采样能力。

具体公平性：

- 同一逻辑 workspace、任务文本、原图 bytes/尺寸/hash、初始帧数、已交付历史和权限；各 arm 独立重置副本，不能共享执行后的环境或记忆。
- 原始文件和正常 read/bash 等既有能力在两边同样可用。旧版可以用自己的方法取证；不能只许新版有效、故意封死旧版替代路径。
- 不给新版额外初始高清图、答案、局部坐标或“请使用 visual_*”提示。模型自己选择是否/在哪里取证；框架按需产生的后续证据和其成本是处理效果的一部分。
- 图生成源码、答案图、环境内部状态和评分器在模型不可访问的 Host 中。模型可以读给定图片/代码，不能直接读 oracle。
- 原图与文本/结构化数据同时存在时两边均可使用。不能藏起本来已有的结构化答案来人为制造视觉需求。
- 两边相同的步骤/工具时间/总 token 限额，不重试到成功。配对顺序预注册为交替/随机 AB、BA；不另花模型调用做缓存预热。

## 4. 任务与验收真值

所有任务只描述用户目标，不提示取证工具。参数、答案、可达终态及变体 seed 在生成前冻结，不能看到 baseline 失败后才挑“有利样本”。

### A. 密集连线图：局部证据能否改善最终追踪

**任务示例：**“沿接线图追踪 J2-3，最终接到了哪个执行器和端口？解释两个交叉位置是连接还是跨越。”

输入是一张真实 raster 的完整接线图，含细线、交叉/接点和端口标签；不是 3×2 像素题。先使用未参与题目调试的确定性图变体，原图两边均可访问。布局需让关键区域可通过一到两次局部检查识别，但不故意提供不足以恢复的信息。独立图拓扑加人工核图给出端点、端口和两个接点的真值，oracle 不进入模型上下文。

模型可以直接答、裁剪、读取数值或用旧版已有工具。实际执行提案并返回真实结果，随后继续作答。主分数是**最终端点/端口与接点解释**；选中相关区域、有没有纠正早期猜测只是原因证据。调用了 inspect、答得更长、或仅描述了图，都不算完成。

能验证：短静态视觉推理中的局部再观察是否带来正确结果/减少错误尝试。不能代表长程交互或一般 OCR 能力。

### B. 压缩后的截图诊断：新问题能否回到正确旧证据

**任务示例：**“升级后任务 K23 不见了。对照升级前后的面板，指出筛选条件和可见性发生了什么变化，并引用正确时刻。”

先通过真实输入入口接纳升级前后截图，另有无关的新时刻作干扰；到固定压缩边界时尚不透露最终问题。原始截图在两边都是合法可访问的输入，摘要和目录按各自生产机制处理，不只删除 baseline 的证据。

预定交互图为：**一次真实生产压缩/摘要调用 → 新问题后的历史定位 → 实际回取/检查 → 最终回答 → 必须的后台结算**。主模型至多三个响应，压缩和后台 review 另各一次，合计最多五次；找到证据可直接回答时提前结束主响应。这样不会为了凑四次总调用而禁止“先找到旧图、再检查、再回答”的合理路径。如果还有不可省略请求，必须在离线预检中列入预算后再冻结，不能作为免费步骤藏掉。摘要不能由评测者手写成恰好丢掉答案的内容；也不能只把候选原图恢复出来再声称模型记忆提升。

最终按正确的前后时刻、真实筛选值、因果定位及证据引用判定。字段真值来自受控 UI 状态和人工核对。把当前图说成旧图、捏造不可见细节、要求用户重传本来保留的图片，分别记录。

能验证：**接纳→压缩→新问题→回取→答案**这一小任务的恢复效果与全程成本，不外推任意长任务的总收益。

### C. 本地反馈面板：探索后能否正确修正行动

**任务示例：**“恢复卡住的 Worker-A，保持 Worker-B 的版本和作业总数不变。”

使用本地可暂停面板，不接完整桌面/ARC。初始截图只显示故障表象；查看详情会揭示下一步应处理的依赖/租约状态。正确完成需要利用实际反馈，错误的重复提交会增加作业数并违反目标。

两 arm 使用同一测试 Host 的普通查看/交互接口和同一状态转移函数；它不能要求只有候选才有的 observation owner 才能使用。候选可额外使用既有视觉记忆/检查；baseline 接收同样的动作回执/截图。实现前先验证旧版也能走该普通 Host 通道；不偷偷回填图片或给候选换一套更安全的世界规则。

所有反馈由真实 renderer/handler 根据模型的实际参数产生。正常动作、无效坐标、错误提交、补观察和不确定状态的分支在 Host 状态图中预注册，不能根据 arm/期望答案选择反馈。正确终态是 Worker-A 运行、Worker-B 版本未变、作业总数未增；同时报告错误动作/重复提交企图、恢复步骤和最终说明。

能验证：有界互动中的证据探索和反馈修正。它不是实时桌面可靠性或新动态宿主已支持的证明。先用状态图核对存在不超过两次必要交互的合法路径，第三个主模型响应可总结；不依赖裁判帮模型发现该路径。

### D. 普通代码任务：日常任务会不会受拖累

**任务示例：**“修复 fixture 项目里空配置导致的异常，保持现有行为，运行已有测试。”

给相同的小型项目、真实失败测试和普通工具，无需图片。验收实际补丁和冻结测试，也检查未要求的修改；不以“进程退出 0”替代需求。该任务用于观察无视觉输入时的正确性、额外步骤、固定合同和历史累计开销。

第二批再加一个有旧截图但没有“图片无关”提示的普通任务，观察模型是否误用视觉。旧 r3 的显式算术提示不能替代此项。

## 5. 固定流程允许完成任务，也允许早停

优先选用能逐步截获 provider 请求、执行真实公共工具的 Runtime/Agent 接缝。生产输入与回执都要离线抓包核对，不重用 r3 的空 workspace/固定假观察 ID 作为完整任务环境。

主模型最多三个响应槽。每槽的转移在生成前固定：

| 本槽结果 | Host 处理 | 后续 |
| --- | --- | --- |
| 模型明确最终作答，或环境按预注册规则自然结束 | 保存后核对结果，不按隐藏答案/arm 选择性停止 | 主模型早停；仍结算本任务的后置/后台 provider 工作，不强行补满主响应 |
| 合法工具批次 | 调用真实 handler，回传其图片/文本/错误；不改写参数 | 进入下一个预定槽 |
| 不合法提案/普通工具失败 | 返回真实校验/权限/执行错误，计入开销 | 有剩余槽才允许模型修正 |
| 第三槽仍需后续推理 | 保留已执行结果，标注未完成/预算边界 | 不追加第四个主模型响应 |
| timeout、缺失 usage、预算耗尽、计划外 provider 请求 | 保存可得 raw 并停止 | 不自动重试/修复/fallback |

每个主模型响应最多两个工具调用，合计最多六个；面板每槽最多一个改变环境的动作。工具参数/区域/是否需要工具由模型选；Host 不发送“现在请裁剪这里/点击这个按钮”的提示，也不预先喂正确反馈。相同 fixture 范围内的普通工具照常可用，不能因 baseline 找到另一条有效路径而判无效。

每 arm 的主响应最多三次，**所有 provider 生成请求合计上限按任务图固定**：A/C/D 最多四次（三次主响应加一次已注册辅助请求）；B 最多五次（三次主响应、一次真实压缩、一次后台 review）。辅助槽的具体用途、位置、模型/路由与输入须在离线预检写明；没有的调用不花，不能运行时改作 repair/外部 judge/child。若某真实路径还需要更多请求，当前实验未就绪，先修方案/预算，不能将后台调用挪到账外。

**主模型停止不是账期结束。** 本任务从输入接纳起，到其前台/后台 provider 工作全部完成或取消并结算为止计费；后台失败/usage 缺失照实标未知。现生产 managed task 在 `session.close()` 后还会排队 memory review（[runner-driven.ts](../../packages/coding/src/task-engine/runner-driven.ts)，`finishRunnerMemoryRuntime` 的 close/reviewDrain 路径），provider observer 和预算不能随最终答案先关闭。两边使用相同初始 Memory 快照，隔离无关待处理作业，用因果归属记录本任务衍生请求并等待 drain；没有可靠结算边界时先补计量接缝，不能宣称全程成本完整。不得为了省账关闭本来启用的后台机制，再当作默认产品成本。生产 memory review 不是外部 eval judge，但其 token/费用仍全部计入。

这是有完整小目标的 Layer 3 受控任务，比较的是该目标从输入接纳到结束的全部过程。它不等价于任意真实项目的无限步 end-to-end；后者只能另做 smoke，不能冒用本次配对结论。

## 6. 首先看效果，再打开成本表

首先盲化输出答案、补丁和最终环境状态，主会话按预注册真值做配对判断；保存理由后再揭盲看 token。不要先按工具次数或便宜程度决定哪边更好。观察轨迹在第二遍用于解释正确/错误的原因。

| 配对结果 | 首先报告的事实 | 再分析什么 |
| --- | --- | --- |
| 两边都做对 | 结果质量是否相当 | 同质量的全程 token/时间差异；有没有可避免的工作 |
| baseline 错、candidate 对 | 是否有实质的新成功/错误纠正 | 多花或节省的完整成本分别列出；失败早停的低成本不算 baseline 更高效 |
| baseline 对、candidate 错 | 可信回退及原因 | 先区分实验设计、provider 波动、产品/提示回退，再决定修什么 |
| 两边都错或未完成 | 真实失败和数据缺口 | 是否题目无效/上限截断了合理路径；不据此宣传省 token |

最终取证后没有改变错误答案、引用了错误时刻、或终态不满足用户约束，不能因调用正确工具算成功。实验因三轮/输出 cap 截断合理解题路径时标注 eval-design/inconclusive，不把“候选取证多”自动判为坏；任何延长须新 revision/新预算、两边同等对待，旧 raw 保留。

pilot 只确认任务有效性和是否值得下一小批。每 arm 每 case 一次不能估算稳定成功率；报告 n/N 与每对原始事实。需要稳健结论时，只为有必要的任务族增加 2–3 个未见变体，并交替调用次序，不自动扩模型面板或只挑候选赢的题。

## 7. 全程 token 必须从第一步记，而不是事后估算

对每个 arm 从输入接纳至全部前后台工作结算的整个任务定义：`T = Σ(每次实际 provider input_tokens + output_tokens)`。计入缓存输入的重传数量；推理 token 如已计入 output 不重复加。压缩、分类、前置及后置模型请求（含 memory review）、错误尝试/恢复均入账；未调用的槽不收费、不补齐。缺失 usage 就标未知，不能用字符/base64 估算补成真实数值。

分项保存：

- 所有请求的 system/messages/tools/内嵌合同；重复传入的历史、目录/标签、工具结果及模型输出。
- 原始/回取/裁剪图像的张数、尺寸、bytes/hash；实际 provider usage 为准，不用 1500/图护栏当图片计费。
- 工具总数、有效取证、无用/重复观察、错误动作、失败恢复；首轮、后续轮及辅助调用分别汇总。
- cached/read/write token、实际可观测费用/额度、用户可见完成时间、后台全部结算时间。缓存和顺序影响单列；订阅名义单价、可见钱包零变化不等于真实费用零。

报告同时包含逐题 Δtoken、同质量完成对、所有尝试的总量，以及回退/新成功对的成本；不能只挑成功样本或用“每成功任务 token”藏掉失败开销。

普通任务和视觉任务分开列。未来评估日常总量时再用实际任务分布加权；没有真实工作负载比例就不宣称整体节省。必要时展示不同视觉任务占比的敏感性，前提是先说明质量是否相当。

## 8. 小批推进与拟议预算（当前授权为 0）

1. **本轮只交付方案。** 原四次预算已经使用；本方案没有发起请求或宣称实验就绪。
2. **零费用准备。** 冻结 A/B/D 各一个实例、真实图片/小项目、独立真值、最短合法解题路径和所有反馈分支；核对 B0/C 生产接线、实际模型映射/路由、输出 cap、完整 usage 与辅助调用图。未经这步不能称在线就绪。
3. **第一批只跑 A+B+D。** 一个视觉模型，每 arm 每题一次，优先比较局部推理、跨压缩视觉记忆这两项主体价值，同时用普通代码任务检查拖累。B 不具备可靠接线/结算时先完成准备，不能静默换回 alpha/算术来宣称测了记忆。跑完先判断任务是否有效，再给效果→成本→建议，不自动追加样本。
4. **第二批按第一批结果决定。** C 的互动反馈与未提示图片的普通任务单独冻结；只有观察到值得解释的差异才加 B1 或新变体，不重做大规模研究/默认全模型 panel。

第一批拟议上限：**26 次 provider 生成请求**（A/D 各2 arm×最多4，B 为2 arm×最多5，含全部辅助请求）；主模型每 arm 最多三轮，每次最多 **2,048 输出 token**；A/D 每 arm **80,000**、B 每 arm **100,000 总 token**，整批 **550,000 总 token**；每请求 **60秒**，A/D 每 arm **5分钟**、B 为 **6分钟**，同 provider 串行；工具每次 **10秒**；**重试/fallback/repair/外部 judge/child 调用均为 0**。metadata HTTP 按类型单列、总计最多 **64 次**，含模型映射/额度/token计数等；预检冻结实际协议后可下调，不能隐含无界探测。

按旧 r3 约12K输入/请求估计，第一批约 **0.30–0.45M token**，只是整个试验的规模估计，不是框架 token 增量或费用。拟议外部追加支出停止上限 **USD2**；必须在执行前核对实际计费/订阅额度观测方法并冻结，不能把本地名义费率或钱包观察当准确账单。未补齐预算核算与实际调用图、未获得新预算时维持 **授权0调用/0 token/0费用**。这些是防跑飞预算，不是预先锁死的采用目标。

## 9. 采用建议如何形成

先确认有无实质结果改善；再逐题解释新增开销是否来自不可避免的新成功，或来自常驻合同、重复送图、过密采样、历史增长和无效重试。必要时只优化观察/工具装配/输出格式，再对受影响题复验，不扩大到 ARC、完整桌面或新规划器。

没有足够收益时建议简化或撤回新增机制；有收益但成本需要改善时建议优化后小批复验；两者兼顾才提出采用建议。**不预先承诺框架一定更聪明或省 token，不以固定百分比替 owner 做决定。** 当前结论是“旧证据不足，新方案待准备/执行”。

### Standards（方案审查）

独立只读复核：成文规范违反 0、smell 判断 0。仅修改方案及状态指针；未追加模型调用，没有将提案预算或方案审查当作行为验证通过。

### Spec（方案审查）

独立复核先发现“最终答复后可能仍有后台 memory review”的账期遗漏，现已补入因果归属、drain、辅助调用图和所有 token；原项关闭。最终剩余关联发现 0，确认首批任务、26次拟议上限与效果→全程 token→方向的判断顺序一致。此处不等于实验输入已就绪或结果已验证。
