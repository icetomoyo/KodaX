# RepoIntel v2：可信且不拖慢 KodaX 的仓库智能

日期：2026-11-23。状态：**阶段 0 已发布（v0.7.97-beta.12）；阶段 1 已完成（2026-11-25，见 §10）；阶段 2 进行中（计划见 §11）。**
基线：`c9589bdc2`（v0.7.97-rc.1）。

## 1. 为什么要重做

用户反馈当前 RepoIntel 不省 token、找不准代码，还会截断导致看不全。2026-11-23 分截断、token、准确性、运行时四路做了只读审计，并在本仓库及临时 fixture 上实跑确认。详细条目在本地未入库的 `docs/research/2026-11-23-repointel-audit.md`，要点如下：

- **不准，但标着高置信度。** 编译器解析出的调用目标被丢弃，callTargets 改由全仓同名匹配重建（`semantic-build-materialize.ts:316-350`）。本仓库 27% 的边是纯同名匹配，会跨语言、指进测试文件。`.js` 的 import 不映射到 `.ts`，于是产生假的模块依赖和假循环。置信度恒在 0.91–0.99。`semantic_lookup` 只是子串匹配。
- **静默截断和伪造结果。** 每个文件最多 40 个符号、每个符号最多 8 个调用方、每个文件最多 12 个 import，签名只取第一行，大文件和未支持语言直接跳过，以上全都没有标记。查不到时返回伪造的 "worker unavailable" 结果。
- **更费 token。** 工作树一脏，每次编辑都全量 `createProgram`（约 10.5 秒、约 2GB），工具只等 2 秒，于是返回 "warming"。注入内容带时间戳，每个编辑任务都会重新追加约 430–1,075 token。
- **运行时问题。** 往用户仓库写约 60MB 的 `.agent/` 且不加 exclude；git 出错时被当成"没变"；大量错误被静默吞掉。

**根因是架构，不是零散 bug。** 现在把整仓全量分析放在每轮请求的关键路径上。后来每一次性能优化（加超时预算、退回同名匹配、加上限、用占位结果兜底）本质上都是不告知地降质量；又没有真值评测，结果越改越差。

v2 的两条总规矩：

1. 性能靠架构解决，不靠降质量。
2. 能力受限时必须告诉模型，不能静默降级。

## 2. 目标与非目标

v2 要回答好 grep 和单点 LSP 回答不好的四类问题：

1. **导航**：精确的定义和引用，跨文件、跨包。
2. **影响面**：传递的调用方和依赖方，带数量和排序。
3. **定位**：在陌生仓库里按概念找代码，用词面检索（标识符按驼峰和下划线拆词，加路径和 doc 注释，做 BM25）。
4. **地图**：按任务相关性排序、控制在 token 预算内的仓库地图。

保留：changed scope 和 changed diff（基于 git，便宜且准）。

**验收线**：在真实任务上，比只用 grep 加 LSP 更省轮次、更省 token，且成功率不降。达不到就不进默认。

**非目标**：

- **embedding / 向量检索。** owner 2026-11-23 决定不做，也不预留向量字段。理由：强模型通过迭代搜索加上仓库地图和 BM25，已经能覆盖大部分概念定位；embedding 要承担本地模型体积、重新 embedding 的新鲜度问题、远程 API 的隐私问题，结果也没有精确性保证。
- 运行时调用追踪、多仓库联合索引。

## 3. 设计原则

1. **诚实契约。** 每个结果都带三个标签：
   - **精度**：`precise`（编译器或 LSP）、`syntactic`（语法加作用域解析）、`heuristic`（同名推测）。
   - **完整性**：完整；或已截断（还有 N 个，附翻页方式）；或未索引（附原因：语言、大小、解析失败）。
   - **新鲜度**：哪些文件的索引已过期。

   "未找到"、"未索引"、"服务不可用"是三种不同结果，必须分开报告，永远不返回占位数据。
2. **请求路径永不等待构建。** 查询只读现有索引。过期文件现场单独分析（单文件毫秒级），或者标为过期后照常返回。
3. **按文件增量，按内容寻址。**
   - 每个文件的分析结果以内容 hash 作 key；改一个文件只重算这一个，再增量更新关系图。
   - KodaX 自己的编辑工具直接通知索引改了哪些文件；外部改动由 watcher 或 git 状态兜底。
4. **分层精度，按需升级。** 语法层覆盖全部语言、始终在线；精确层只针对被问到的符号按需计算，结果缓存。
5. **资源上限是硬约束。**
   - 独立进程，调低 OS 优先级，设内存上限，主代理请求进行中时让出资源。
   - 不写用户仓库。
6. **质量门禁先于功能。** 先建真值评测和性能基准。精确率、召回率或性能预算任何一项回退，都不能合入。

## 4. 架构

```text
L0 清单层   git ls-files + 目录级 Merkle hash；编辑工具事件 + watcher 兜底
L1 语法层   tree-sitter：定义 / 引用 / import / 完整签名 / doc 注释，单文件毫秒级
L2 解析层   真实模块解析（tsconfig paths、package exports、.js→.ts、Python 包、Go module、Cargo），
           作用域内名字解析；每条边标注证据类型
L3 精确层   按需：通过 Host 现有 LSP 服务（packages/coding/src/lsp/service.ts）解析被查询的符号，
           结果按相关文件 hash 回写缓存
查询层      定义 / 引用 / 调用方（带深度和计数）/ 影响面排序 / BM25 定位 / 仓库地图
```

### 4.1 实现形态与进程归属（已定）

- **语言：Rust。** 核心做成 Rust crate 并编译成独立二进制，复用现有 native 二进制的发布链路（与 `native/windows-sandbox-v2` 同一种形态）。
- **归属：由 Host 管理的子进程。**
  - 每个 Host 一个，按仓库管理索引，Host 上所有会话共用。
  - Host 负责拉起、监管、空闲回收和资源限额。
  - 生命周期跟随 Host，不新增独立 daemon。
- **独立可用。** low-level inline 调用方可以直接拉起该二进制，保持包的独立可用性。
- **分工：**
  - Rust 进程负责 L0–L2、存储和查询，不接触 LSP。
  - L3 由 Host 侧组合：用现有 LSP 服务解析，结果写回索引缓存。
- **磁盘缓存：** 放在 KodaX 数据目录，按仓库分开，按内容 hash 寻址；不同 profile 的 Host 可以复用文件级分析结果。

被否决的方案：

| 方案 | 否决理由 |
|---|---|
| Host 进程内 napi | 崩溃会拖垮所有会话；大内存和 CPU 跟 Host 抢，无法单独限额 |
| 独立全局索引 daemon | 要重复 Host daemon 已付出的所有权、版本兼容、Windows Job 监管和崩溃恢复成本；收益只在多 profile 并发同一仓库这种少见场景 |
| 每进程/每会话一个（现状） | 内存翻倍，重复冷启动 |

### 4.2 语言分级（已定）

| 级别 | 语言 | 覆盖层 |
|---|---|---|
| 首批一等 | TS/JS、Python、Go、Rust | L1 + L2 + L3（有语言服务器时） |
| 语法层 | Java、C++ | 只有 L1，结果标注 `syntactic`/`heuristic` |
| 其他 | tree-sitter 有语法的语言按需加入 L1 | 未支持的语言在结果中报告为"未索引" |

### 4.3 与 Agent 的接口

- **自动注入：**
  - 会话开始时注入一张小而稳定的仓库地图，不带任何时间戳，只在结构变化时重新生成，以命中 prompt cache。
  - 之后的任务只在内容确实变化时发增量。
- **工具：**
  - 按导航、影响面、定位、地图四种职责收敛，替代现在 RepoIntel 加 LSP 共 20 个工具（约 3.4k token 的定义）。
  - 具体怎么合并，用评测决定。不能隐藏某个工具后，逼模型多一轮发现才能拿到完整信息。
- **输出：** 紧凑、排序、可翻页，带精度标签；没有内容的行不打印。
- **索引没建完时：** 引擎状态不是 ready（冷索引中，或降级）时，工具不返回结构化结果，只告诉模型索引还没好，请用 grep 和 read。原因是不完整的结果看起来像完整的：模型查不到某个调用方，会以为它不存在。（用户 2026-11-25 确认）
- **提示词：** 定位成 grep 和 read 的补充，不要求先用结构化工具。按 ADR-033 写并补 eval。

## 5. 性能预算（目标值，以基准实测为准）

| 指标 | 目标 |
|---|---|
| 请求路径新增延迟 | 温索引查询 p95 < 50ms；永不等待构建 |
| 编辑后增量 | 单文件语法层 < 100ms |
| 冷启动 | 后台进行，永不阻塞请求；时间可以长，1 万文件的语法层在一分钟左右（用户 2026-11-25 确认） |
| 内存 | 1 万文件规模的仓库，索引进程 ≤ 300MB |
| 磁盘 | 不写用户仓库；体积远小于现在的 60MB |
| 安装包 | 二进制加语法库的增量要实测，作为发布门禁之一 |

## 8. 阶段 0 范围（对旧引擎）

1. **默认只保留 overview、changed_scope、changed_diff，并修复：**
   - 注入内容去掉 `analyzedAt` 和 `generatedAt`。
   - changed_scope 支持翻页。
   - git 状态未知时按"有改动"处理。
2. **退出默认：**
   - 工具：module_context、symbol_context、process_context、impact_estimate、semantic_lookup、relationship_scan、cyclic_dependencies。
   - 自动注入里的 module/impact。
   - 默认不再后台构建语义索引。
   - SDK 显式启用时仍然可用。
3. **诚实输出：**
   - 截断处标出"还有 N 个"。
   - 区分"未找到"和"服务不可用"，删除 `buildLimited*` 占位结果。
   - 查不到模块时报错，不再返回最大的模块。
4. **存储：** 移出用户仓库（至少写入 `.git/info/exclude`）；校验 `target_path`；删除只写不读的 index 文件。
5. **提示词：** 删去 "concepts rather than exact strings"、"before grepping"、"read/grep only after structured tools"；changed_scope 加上复用已注入 scope 的说明。按 ADR-033 写并补 eval。
6. **文档：** 关闭或重写 KNOWN_ISSUES #133，它引用的代码已经不存在。

### 8.1 实施结果

- **开关：** `auto`（默认）只开放 overview、changed_scope、changed_diff；显式 `full` 或 `light` 才开放语义工具、module/impact 注入和预热。直接调用 SDK 的 `getModuleContext` 等函数仍把 `auto` 当作 `full`，因为调用本身就是显式请求。
- **存储：** 默认写到 `<config home>/repo-intelligence/<目录名>-<路径哈希12位>`，不再写进用户仓库，因此不需要 `.git/info/exclude`。`KODAX_REPO_INTELLIGENCE_STORAGE_DIR` 可以覆盖；相对路径表示调用方有意放回工作区。`target_path` 超出执行目录和 Git 根目录时报错。删除了 `changed-scope.json`、`module-index.json`、`symbol-index.json`、`process-index.json` 这几个只写不读的文件。
- **错误语义：** 索引没响应时抛 `RepoIntelligenceUnavailableError`（`warming` 或 `unavailable`），worker 返回的"未找到"走 `RepoIntelligenceQueryError` 原样透出。relationship_scan 只在前者时停止并提示改用 read/grep/LSP。
- **KNOWN_ISSUES #133：** 以 Won't Fix 关闭，所指的测试和缓存已删除。

### 8.2 旧引擎基线（2026-11-23，KodaX 仓库，`npm run bench:repo-intel-truth`）

真值来自 TypeScript 编译器，覆盖 3,383 个源文件、20,355 个单元、25,841 条调用边。

| 关系 | 范围 | 精确率 | 召回率 |
|---|---|---|---|
| 调用目标 | 抽样 300 个符号 | 42.7% | 55.1% |
| 调用目标 | 全部 19,593 个符号 | 29.3% | 48.7% |
| 调用方（symbol_context 展示的每条 8 个） | 抽样 300 个符号 | 75.3% | 44.1% |
| 模块依赖边 | 全部 | 70% | 63.6% |

- 每个文件最多索引 40 个符号，79 个文件共丢掉 2,984 个符号。
- `.js` 后缀的 import 没有解析到 `.ts`，所以每个包都多出一条指向根模块 `.` 的假边，唯一报出的依赖环也是假的。

## 9. 开工时的决定（2026-11-24 用户确认）

体积实测（2026-11-24，Windows，发布用的编译设置）：程序本身 0.13 MB；rusqlite（bundled）+1.70 MB；语法库 TypeScript 含 TSX 2.93、JavaScript 0.49、Python 0.54、Go 0.30、Rust 1.19、Java 0.49、C++ 3.50 MB；七种全部 9.07 MB，再加 SQLite 10.77 MB（gzip 后 1.88 MB）。现在的 npm 包把五个平台的原生程序放在同一个包里，`0.7.97-rc.2` 解压后 35.0 MB，其中原生程序 4.5 MB。

1. **存储：rusqlite（bundled）。** 增量更新、写到一半崩溃不坏库、多读者都是现成的。bundled 的 SQLite 编译时开了 FTS5，阶段 4 的 BM25 直接用它。
2. **进程协议：JSON-RPC 2.0，消息前带 `Content-Length` 头（和 LSP 一样）。** Host 侧用 LSP 客户端已经依赖的 `vscode-jsonrpc`，请求配对、取消和错误处理都现成。
3. **降优先级和内存上限：三个平台同一套做法。**
   - 降优先级：只降索引线程，回答请求的线程保持普通优先级，不需要特权。Windows 用线程的 `THREAD_PRIORITY_IDLE`；Linux 用线程的 nice 10 加磁盘 IO 的 idle 级；macOS 用线程级的 `PRIO_DARWIN_BG`。最初是整个进程进入后台模式，第 7 层实验后改成这样，见 §10.4（用户 2026-11-25 同意按实验结果选）。
   - 内存：索引进程的内存靠设计封顶：不保留语法树，每个打开的仓库只有两个各约 16 MB 页缓存的连接。它不会在接近预算时自己收缩。Host 每隔几秒读它的实际内存，超过 300 MB 预算只报告，不结束它（见 §10.3 Host 侧）。
   - 不单独给 Windows 套带内存上限的嵌套 Job：Linux 和 macOS 没有不需要特权的对等手段，硬上限还是要靠 Host 监视。Linux 的 `RLIMIT_AS` 按虚拟地址空间计，SQLite 和 Rust 的预留会被误判成超限。
   - 索引进程是 Host 的子进程，本来就在 Host 的 Job 里，Host 退出它跟着退出，这部分不用写代码。
4. **语法库和安装包。**
   - 语法库静态编进程序，不在运行时加载外来原生代码。
   - RepoIntel 不做成扩展。接入代码（拉起和监管进程、地图注入、工具、L3）留在核心里；原生程序是可以缺的组件，缺了就退回只用 git 的工具面，并如实报告"未索引"。
   - 阶段 1、2 放在开关后面，原生程序不进 npm 包，CI 为五个平台编出来放进 GitHub Release 的附件。
   - 默认打开之前按评测结果二选一：值得默认打开就按平台拆包（npm `optionalDependencies`，和 Claude Code、Codex 一样）；只对部分人有用就做成按需下载的组件（和 pi 下载 rg、fd 一样）。
   - 现有的必需原生程序（Windows 沙箱 helper、文本事务）留在主包里，不拆出去：它们缺了 Host 起不来，拆出去会让离线环境里漏同步一个包变成装好了却打不开。
   - 离线安装（客户里有离线环境，用户 2026-11-24 要求）：
     - 单文件版：GitHub Release 每个平台的压缩包里同时放 RepoIntel 程序，拷一个包就齐了。离线环境首推这个。

     - 如果选了按需下载：另外提供本地文件安装，指定从 Release 下载的压缩包，用主包里记下的哈希校验。

## 10. 阶段 1 实施计划（2026-11-25）

### 10.1 分层提交

### 10.2 引擎协议（阶段 1）

| 方法 | 作用 |
|---|---|
| `initialize` | Host 给出存储根目录和内存预算；引擎回版本和支持的语言 |
| `workspace.open` / `workspace.close` | 开始或停止维护一个仓库的索引；后台进行，立即返回 |
| `workspace.status` | 状态（索引中 / 就绪 / 降级）、已索引和过期文件数、按原因分组的未索引文件、引擎自报内存 |
| `files.changed` | Host 的编辑工具通知改了哪些文件 |
| `symbols.definitions` / `symbols.references` | 按名字查；每条带精度，整体带完整性和新鲜度 |
| `file.outline` | 一个文件的定义、签名和注释；文件过期就现场重新分析 |
| `file.imports` | 阶段 2 新增：一个文件的 import 及解析到的文件或目录（见 §11.3、§11.4） |

- 阶段 1 的引用都是名字匹配，标为 `heuristic`；定义标为 `syntactic`。
- 外部改动的兜底：引擎在后台定期比对清单里文件的修改时间和大小，并重跑 `git ls-files` 发现新文件。阶段 1 不引入文件监视库。

### 10.3 未经用户确认的实现选择

- **开关：** 环境变量 `KODAX_REPO_INTELLIGENCE_ENGINE=v2`。打开后 Host 拉起引擎并维护索引。阶段 1 不改 Agent 看到的工具和提示词，地图注入和工具在阶段 2 起接入，所以本阶段不需要提示词 eval。
- **内存：** 引擎自己报 RSS，Host 定时读取，这样 Host 不用为读别的进程的内存加新的原生代码。超过预算只报告。持续不回答，Host 才结束它并退避重启。引擎不保留语法树，每个仓库的 SQLite 页缓存有上限，所以内存随打开的仓库数增长，靠按仓库闲置关闭来封顶。
- **进入下一阶段的门槛：** 阶段 1 没有 L2 的模块解析，调用边只能是名字匹配，跟旧引擎比调用边精确率不公平。门槛定为：
  - 在 KodaX 上按编译器真值，定义的精确率和召回率都要高于旧引擎（旧引擎每个文件最多 40 个符号）；
  - 每条引用都标 `heuristic`，没有静默截断；
  - 性能达到 §5 的预算（KodaX 和 `microsoft/vscode`）。
  - 调用边照常统计，只作为阶段 2 的基线。
- **存储位置：** `<config home>/repo-intelligence-v2/<目录名>-<路径哈希12位>/index.sqlite`，和阶段 0 的旧存储分开。
- **大纲的范围：** 阶段 1 的签名就是定义所在的那一行，去掉首尾空白，最长 200 个字符。阶段 1 不提取 doc 注释和 import，留到 L2 再做，因为它们要按节点去补。阶段 1 的门槛只看定义，所以缺这两样不影响门槛。
- **新鲜度：** 状态里不报过期文件数。要报这个数就得逐个 stat 文件，代价和一次全量扫描一样。改为每条命中自己带 `stale`：查询时比对该文件现在的大小和修改时间。`file.outline` 遇到过期文件就现场分析，并通知索引跟上。
- **翻页：** `limit` 默认 50，最大 500。回答带 `total`、`offset` 和 `nextOffset`（没有下一页时为 null）。回答还带 `coverage`：索引状态、已索引数、有语法错误的文件数，以及按原因分组的未索引数。
- **Host 侧（第 6 层）：**
  - 找程序：先看 `KODAX_REPO_INTELLIGENCE_ENGINE_PATH`，再按现有原生程序的位置找（`native/<平台>`、`dist/native/<平台>`、可执行文件旁的 `vendor/kodax-native/<平台>`），最后找源码目录里 `cargo build --release` 的产物。阶段 1 程序不进 npm 包，所以需要这个环境变量。程序不做哈希校验：它只读仓库、只写自己的存储目录，和沙箱 helper 不同。
  - 监管：第一个 Run 打开仓库时才拉起。每 5 秒读一次 `engine.status`，兼作心跳。回答请求的线程是普通优先级，但机器很忙时仍可能慢几秒，所以错过一次不算卡死，持续 30 秒没有回答才结束它。引擎退出或卡死后，从 1 秒起每次翻倍、最长 5 分钟后重启，并重新打开原来的仓库。稳定运行 10 分钟以上再出错，等待时间从头算。
  - 起不来（程序不存在、不能运行、拒绝初始化、协议不符）不靠定时器重试：引擎回到空闲，下一次使用时再试，两次尝试之间仍按上面的退避间隔。程序缺失时不会每隔几分钟白白拉起一次、写一条日志。
  - 内存只报告不强制：超过预算（默认 300 MB）时写入状态和日志，不结束引擎。原因：引擎没有收缩缓存的机制，内存主要随打开的仓库数增长；结束它再重新打开同样的仓库，内存会回到同样的水平，形成重启循环，索引永远建不完。第 7 层在 `microsoft/vscode` 上实测后决定不加硬上限，见 §10.4。
  - 按仓库闲置关闭：每个仓库记最后使用时间，任何工具调用都算使用，所以只用 shell 改文件的长 Run 也会一直被扫描。某个仓库 10 分钟没用就单独关掉（`workspace.close`），最后一个关掉时停掉引擎。这样内存和 15 秒一次的后台扫描都只与在用的仓库数相关。重新打开时只补扫变化的部分（KodaX 无变化约 124 ms）。
  - 版本配套：`initialize` 回 `protocol`（目前为 1），Host 对不上就不用它，在状态和 doctor 里提示重启 KodaX，正常使用不受影响。这对应应用更新后 Host 没重启、拉起了新版程序的情况。索引文件名带格式版本（`index-v<版本>.sqlite`），不同版本的引擎即使共用存储目录也不会互相删表重建；打开仓库时删掉更旧版本的文件，删不掉（旧引擎还开着）就下次再删，更新版本的文件保留。
  - 编辑通知：`run.started` 打开该 Run 的仓库（会话的 gitRoot，没有就用执行目录）；`tool.finished` 里文件工具记下的改动路径换成仓库内的相对路径后转给引擎。shell 命令改的文件靠引擎 15 秒一次的扫描跟上。路径不在该仓库内的改动（例如在别的 worktree 里）不转发。
  - 引擎启动时到达的编辑通知会丢掉，因为打开仓库时本来就会全量扫描一遍。
  - `kodax doctor` 报告开关、程序在哪或在哪些位置找过，以及把程序拉起一次读到的版本、语言和后台优先级。程序缺失或起不来只报告，不让 doctor 失败。

### 10.4 第 7 层评测结果（2026-11-25）

确定性评测，不调用模型。命令：
- `npm run bench:repo-intel-v2-truth`：用编译器真值测准确率。
- `npm run bench:repo-intel-v2`：测性能。

测试机是 Windows x64（24 核，NVMe），引擎为 release 构建。原始结果在本地 `%TEMP%/kodax-draft/l7/`。

**定义（KodaX，3,469 个 TS 文件，21,659 个单元，与旧引擎比较同一个集合）**

| 引擎 | 精确率 | 召回率 | 行号一致 |
|---|---|---|---|
| v2 | 把真实的局部声明算对 99.6%；只认真值列出的顶层单元 89.0% | 99.9%（漏 25 个） | 100% |
| 旧引擎 | 100.0%（1 个误报） | 85.9%（漏 3,053 个） | 100% |

- 真值只列顶层单元（顶层函数、类及其方法、接口、类型、枚举）。v2 报告每个作用域里的定义，所以严格口径下的"误报"大多是对的。评测用语法树逐条核对 v2 多出来的 2,662 个：
  - 2,575 个是真实的局部声明，例如测试回调里的函数、对象字面量的成员、函数里的类。
  - 87 个是 `x.y = () => …` 这类把函数赋给属性的写法，全在测试和 bench 里。语法库自带的 tags 规则把它算作定义，行号也指向那次赋值。
  - 容器归错的有 0 个。
- 漏掉的 25 个都是 `packages/llm/src/providers/openai.ts` 里的方法：tree-sitter-typescript 0.23.2 在这个文件上报语法错误，类体在第 411 行提前结束。
- 按种类的召回率：
  - 方法 98.5%，旧引擎 67.2%；
  - 函数、类、接口、类型、枚举都是 100%；
  - 旧引擎在其余种类上 75%–96.5%。
- 评测过程中修了三处：
  - 构造函数和类字段里的定义曾被算成类的方法，有 31 个误报，现在不会了；
  - `#private` 方法纳入索引；
  - 单文件大小上限从 1 MiB 提到 4 MiB。原因是 KodaX 的 `src/sdk-runtime.ts` 有 1.12 MB（725 个单元因此漏掉），vscode 的手写测试有 1.5–2.5 MB；8.4 MB 的生成夹具仍不索引。依据见下面"单文件大小上限"。
  - 修完后索引格式升到 6。

**调用方（抽样 300 个导出函数和方法，阶段 2 的基线）**

| 来源 | 精确率 | 召回率 |

**引用契约：**
- KodaX：抽样的 300 个名字全部翻页取完，共 306 页、9,390 条，最大的 total 是 2,854。

- 每一页都标 `heuristic`，翻页取到的条数都等于 `total`。

**性能（最终版程序：只降索引线程）**

| 指标 | KodaX（3,721 个文件） | vscode（16,737 个文件，提交 1f8d8b21） | 预算 |

| 建完 / 查询后 / 编辑后内存 | 26 / 31 / 25 MB | 31 / 46 / 32 MB | ≤ 300 MB |

| definitions / references 首页 / outline 的 p95 | 2.1 / 2.5 / 0.8 ms | 2.6 / 2.8 / 1.0 ms | < 50 ms |

| 用磁盘上的索引重新打开 | 205–258 ms | 1.3 s | — |
| 程序大小 | 12.2 MB（Windows x64，含七种语法库） | | 实测 |

评测还改了三处：

- **内存上报。** Windows 的后台模式曾把工作集压在 32 MB 左右，多出来的页被挪出工作集。引擎原来报工作集，所以在 vscode 上一直报 32 MB，从外部量到的私有内存却是 94 MB。Host 的预算检查拿这个数永远触发不了。现在 Windows 上报私有内存，Linux 和 macOS 仍报常驻内存。
- **WAL 文件。** SQLite 原来把 WAL 留在写过的最大一批的大小，vscode 上有 41.5 MB。现在设了 `journal_size_limit` 4 MB，检查点之后就截回去。仓库关闭时 WAL 会被删掉。
- **内存硬上限：不加。**
  - 1.67 万文件的 vscode 峰值是 109 MB，离 300 MB 还远。
  - 内存主要来自每个打开仓库的 SQLite 页缓存（上限 16 MB）和索引时的临时数据，靠按仓库闲置关闭来封顶。
  - 结束引擎再重开，内存会回到同样的水平。
  - 所以维持第 6 层"超过预算只报告"的做法。

**优先级实验（2026-11-25，vscode 冷索引，实验用构建按环境变量切换模式）**

原来整个进程进入后台模式。实验比较了五种做法，每格一次，同一台机器上同一模式两次之间能差 20–30%，所以只看大的差别：

| 做法 | 空闲时冷索引 | 24 核 CPU 跑满时冷索引 | CPU 跑满时查询 p95 / 最慢 | 磁盘写满时冷索引 |
|---|---|---|---|---|
| 整个进程后台模式（原来） | 73–145 s | 88–113 s | 31 / 60 ms | 95–97 s |
| 整个进程 IDLE 级 | 42–51 s | 62–70 s | 97 ms / 11.5 s | 47–49 s |
| 普通优先级 | 41–47 s | 49–56 s | 29 / 65 ms | 45 s |
| 只降索引线程，后台模式 | 77 s | 104 s | 17 / 22 ms | — |
| **只降索引线程，IDLE 级（采用）** | 48 s | 65 s | 18 / 29 ms | — |

- 负载这边：CPU 负载（每核算 SHA-256，基线 20–27 s）和磁盘负载（2 万次 4 KB 同步写，基线 17.5–18.1 s）在任何模式下都没有超出误差的变慢。引擎只有一个索引线程，在 24 核上最多占 1/24，量不出来；核少的机器上降优先级的作用会更明显。
- 后台模式慢在磁盘和内存：它同时降了磁盘 IO 和内存优先级，并把工作集压到 32 MB。磁盘有负载时冷索引慢一倍，而写负载本身没有变快。
- 整个进程降优先级的隐患：回答请求的线程也被降了。CPU 跑满时，IDLE 级下查询最慢一次等了 11.5 秒，十几秒只回答了 158 次（其他模式 700 次以上）。
- 所以只降索引线程，回答请求的线程保持普通优先级。查询遇到过期文件时当场重新解析，也在普通优先级上做，不受索引线程影响。
- Linux 改成同样只降索引线程（nice 10 加 IO idle 级，两者在 Linux 上本来就按线程算）。macOS 改成线程级的 `PRIO_DARWIN_BG`。这两个平台没有机器实测，只做了交叉编译检查，第 8 层的 CI 会在真机上跑测试。

**单文件大小上限 4 MiB**

- 真实仓库里超过 4 MB 的文件：
  - KodaX 手写代码最大的是 `src/sdk-runtime.ts` 1.12 MB；
  - vscode 手写测试最大 2.5 MB，超过 4 MB 的只有 8.4 MB 的生成夹具 `test-checker.ts`；
  - `node_modules` 里有 `typescript.js` 9.1 MB、`_tsc.js` 6.2 MB，但它们被 `.gitignore` 排除，本来就不进清单。
- 大文件实验（放开上限，单独索引一个文件）：

| 文件 | 大小 | 索引时间 | 内存峰值 |
|---|---|---|---|
| `src/sdk-runtime.ts` | 1.12 MB | 0.3 s | 31–34 MB |
| `_tsc.js` | 6.2 MB | 1.1 s | 163 MB |
| `test-checker.ts` | 8.4 MB | 1.3 s | 193 MB |
| `typescript.js` | 9.1 MB | 1.7 s | 253 MB |

  内存峰值约是文件大小的 28 倍，来自语法树。4 MiB 的文件约 110 MB，加上引擎平时的几十 MB，仍在 300 MB 预算内；9 MB 的文件一个就接近预算。
- 其他工具（读了源码或官方文档）：
  - 做索引的工具都按大小跳过文件：GitHub 代码搜索 350 KiB，Sourcegraph 1 MB，zoekt 2 MiB，Continue 5 MiB（也用 tree-sitter，和我们最接近）。zoekt 和我们一样把跳过的文件记下原因。
  - Agent 的读文件工具不按大小拒绝索引，而是限制一次返回给模型的量：Claude Code 的 Read 一次最多 25,000 token、整文件读超过 256 KB 要分段；Codex 没有索引，工具输出截到 10,000 token；pi 没有索引，读文件一次 2,000 行或 50 KB。
  - ripgrep 和 universal-ctags 默认不限大小。
- 超过上限的文件不是看不到：状态里按"size"计数，`file.outline` 对它回答"未索引：size"，模型照样可以用 grep 和 read 分段读。

**对照 §10.3 的门槛：**
- 召回率远高于旧引擎。
- 精确率按严格口径低于旧引擎，因为 v2 多报了真值不列的作用域。用语法树核对后，v2 没有位置错误的定义，只剩 87 个属性赋值（0.4%）不是声明。
- 引用契约满足。
- 性能都在预算内且余量很大。冷索引按用户确认的预算（不阻塞请求，可以更长）满足，vscode 约 30 s / 万文件。

**结论：** 阶段 1 通过，可以进第 8 层。

- 用户 2026-11-25 确认的：
  - 精确率按"把真实声明算对"的口径，v2 保留局部定义；
  - 冷索引不阻塞请求，可以更长；
  - 索引没建完时工具不给结构化结果，让模型用 grep 和 read（见 §4.3，阶段 2 加工具时实现）；
  - 优先级按实验选，选的是"只降索引线程"；
  - 单文件大小上限 4 MiB（依据见上）；
  - WAL 上限 4 MB；
  - Windows 上报私有内存；
  - 不加内存硬上限。

### 10.5 第 8 层：构建和发布（2026-11-25）

- **单独的构建命令：** `npm run build:repo-intel`，不并进 `build:native`。`build:native` 在日常 `npm run build`、Full CI 和 npm 包聚合里都会跑，并进去会让这些地方都多编一遍引擎，可 npm 包根本不带它。
- **产物：** `dist/repo-intel/<平台>-<架构>/`，里面是程序、`LICENSE-APACHE-repo-intel.txt`，以及 `THIRD-PARTY-NOTICES-repo-intel.txt`（41 个编进程序的依赖的许可证原文；只在编译时运行的过程宏不算）。C++、Java、TypeScript 三个语法库发布的 crate 里没带许可证文件，原文从上游仓库拷到 `native/repo-intel/licenses/`；以后再有依赖缺许可证，构建直接失败，不会发出没有声明的程序。`npm run build` 清理 `dist/` 时保留 `dist/repo-intel`，和 `dist/native` 一样，所以先编引擎再 `npm run build:binary` 也不会丢。目录不叫 `dist/native/`，因为 package.json 的 `files` 带着 `dist/native`。
- **进单文件版：** `build-binary` 把它拷到可执行文件旁的 `vendor/kodax-native/<平台>/`，Host 本来就在那里找。目录里没有引擎时照常打包，只打印一行；Release 流程在打压缩包时要求它存在。打包后的自检会打开开关跑一次 `kodax doctor --json`，要求报出版本，且后台优先级生效。
- **不进 npm 包：** npm 包的审计脚本见到 `kodax-repo-intel` 就失败。npm 用户要用引擎，就从 Release 压缩包里取出程序，设 `KODAX_REPO_INTELLIGENCE_ENGINE_PATH`。
- **Linux：** 和原生文本组件一样，在钉死摘要的 `manylinux2014` 容器里编译（`build-linux-native.mjs repo-intel`），再过 glibc 2.17 检查。
- **真机测试：** Release 流程在五个平台上都跑 `cargo test --release`。Linux 和 macOS 的线程优先级、进程内存这些测试，第一次在真机上跑就是下一次 Release 或手动触发的构建。

## 11. 阶段 2 实施计划（2026-11-25）

范围按 §7：L2 模块解析、仓库地图注入；按 §4.3 给 Agent 加导航工具。全部仍在 `KODAX_REPO_INTELLIGENCE_ENGINE=v2` 开关后面。退出条件：任务 A/B 赢过只用 grep 加 LSP。

### 11.1 分层提交

1. 本节计划。
2. L1 补 import：每个文件记下导入了什么（模块说明符、导入的名字、本地别名）。只给首批四种语言提取，Java、C++ 没有 L2，提取了也没人用。
3. L2 TS/JS 模块解析：相对路径、`.js` 写成 `.ts`、目录的 index 文件、tsconfig 的 `paths` 和 `baseUrl`、workspace 包名按 package.json 解析到源码。产出文件级的 import 边，每条带证据（解析到了，或者没解析到及原因：外部包、找不到）。按编译器真值评测 import 边（旧引擎 70% / 63.6%）。
4. L2 Python、Go、Rust 模块解析：Python 的包目录和相对导入，Go 的 `go.mod` 模块路径，Rust 的 `mod` 声明、`crate::` / `super::` 路径和 Cargo workspace 的 crate 名。用小型夹具测；这三种语言的真值集按 §9 第 5 条另做。
5. 引用解析：一个名字先找本文件的定义，再顺着 import（含多跳 re-export）找到被导入文件里的定义，都找不到才退回同名匹配。解析到的引用标 `syntactic`，同名匹配仍标 `heuristic`。新增"某个定义的引用"查询。按编译器真值评测调用方（阶段 1 基线 34.4% / 97.5%），要在召回率基本不降的前提下提高精确率。
6. 仓库地图：引擎按 import 图给文件排序（PageRank），每个文件列出排在前面的定义及签名，控制在 token 预算内。输出只取决于索引内容，不带时间，同样的索引得到同样的文本。
7. Host 到工具的通道：supervisor 增加查询；`KodaXContextOptions` 增加可选的 RepoIntel 查询服务，Host 在 `buildRunOptions` 里注入，做法和 `lspService` 一样。索引不是 ready 时，查询直接回"还没好"，工具只告诉模型去用 grep 和 read。然后加导航工具。
8. 地图注入：放进 Managed Run Context，和现有的 Repository Intelligence 段放在一起。新会话注入一次，之后只在内容变化时重述，沿用现有的变化检测。索引没好时不注入。
9. 评测：先用 Layer 2 提示词 eval 检查工具说明和地图（ADR-033），再做任务 A/B。A/B 的用例、模型和预算先给用户确认再跑。

### 11.2 未经用户确认的实现选择

- **工具形态：** 先加两个工具：`find_symbol`（按名字查定义，可选带上引用，按文件分组、可翻页）和 `file_outline`（一个文件的定义和签名）。都不延迟加载，因为延迟会让模型多一轮才能看到完整说明。LSP 工具保持原样；A/B 的基线就是 grep 加 LSP。影响面和 BM25 定位按 §7 留到阶段 3、4。
- **索引没好时的回答：** 工具返回正常结果（不是错误），说明索引在建、已索引多少文件，请用 grep 和 read。地图同样不注入半成品。
- **地图预算：** 先定 1,024 token 左右，用 eval 调。只列文件和定义，不列行号以外的细节；没有定义的文件不打印。
- **地图稳定性：** 只有排进地图的文件或它们列出的定义变了，地图文本才会变。普通编辑改的是函数体，地图不变，不会引起重述。
- **语言范围：** L2 做首批四种语言（TS/JS、Python、Go、Rust）。Java、C++ 只有语法层，引用仍是同名匹配，按 §4.2。
- **import 的存储：** import 跟着文件内容存（按内容 hash），解析结果跟着文件路径存，因为同一份内容放在不同位置解析结果不同。新增文件、删除文件或 tsconfig、package.json、go.mod、Cargo.toml 改动时，重新解析受影响的文件。
- **re-export 不单独标记：** `export { a } from './x'`、`export * from './x'`、Rust 的 `pub use`、Python 包里 `__init__.py` 的 `from .x import a`，都按普通 import 记。查名字时，被导入的文件里找不到定义，就顺着它自己的 import 继续找。这样不区分导出与否也不会找错：TS 和 Rust 里，一个文件只 import 没 export 的名字，别的文件拿不到，编译器会报错，能编译的代码里没有这种链；Python 本来就能从模块里取到它导入的任何名字。
- **用哪份 tsconfig：** 每个文件用离它最近的那个目录里的 `tsconfig.json`（没有就用 `jsconfig.json`），顺着相对路径的 `extends` 合并。同目录下的 `tsconfig.test.json` 这类文件不看，也不按 `include` 判断文件归哪份配置。代价见 §11.3 剩下的 7 对差异。
- **构建产物找回源码：** import 指向 `dist/`、`lib/`、`build/`、`out/` 里的文件（或 package.json 的 `exports`、`main` 指向那里）时，先按最近配置的 `outDir` → `rootDir`，再把这一层目录换成 `src/`，找到源码就算解析到。模型要看的是源码，构建产物通常也不在 git 里。
- **重新解析的范围：** 有文件新增或删除，或任何 tsconfig、jsconfig、package.json 被重新读过，就重新解析全部 import；否则只重新解析内容变了的文件。KodaX 仓库冷索引（含一次全量解析）实测 9.0 秒，第 2 层结束时是 8.4 秒。
- **`file.imports` 的未索引原因：** 磁盘上没有这个文件回 `missing`；文件在但索引还没扫到回 `pending`；其余沿用文件自己的未索引原因（`size`、`binary` 等）。
- **解析到目录：** Go 的 import 指向一个包，也就是一个目录；Python 没有 `__init__.py` 的命名空间包也是目录。这两种解析结果带 `folder`，不带 `target`，不硬挑目录里的某个文件。
- **子模块作为导入的名字：** `from pkg import models`、`use crate::store::{sqlite}` 里导入的名字本身可能就是子模块。引擎对每个导入的名字再解析一次，解析到别的文件或目录就单独记一条边；否则这个名字跟着模块走。
- **Python 的查找根：** 绝对导入依次在这些目录里找：文件顶层包的上一级目录（脚本、测试从这里跑）、各个项目目录（有 `pyproject.toml`、`setup.py` 或 `setup.cfg`，文件所在的项目优先）和它们的 `src`、仓库根目录。普通模块和包优先于命名空间包。哪里都找不到时：第一段在仓库里有，就算 `missing`；否则算 `external`。
- **Python 推测根的边界：** "顶层包的上一级目录"只是对脚本目录的猜测。顶层包嵌在仓库深处时（如 `plugins/platforms/email/`），这个目录只用来找到模块，不用来判定 `missing`；标准库同名的模块也不在这里找。引擎内置 Python 3.12 的 `sys.stdlib_module_names`（212 个公开名字）。例如 `plugins/platforms/discord/adapter.py` 的 `import email` 是标准库，不是仓库里的 `plugins/platforms/email/`；`telegram` 插件里的 `from telegram.ext import …` 是外部库。
- **Rust 的模块树：** `self`、`super`、`crate` 分别从文件自己的模块、上一级模块和 crate 根开始。第一段是本模块的子模块文件，就从那里开始；是 workspace 里某个 crate 的名字（Cargo.toml 的 `[lib] name`，否则 `[package] name`，`-` 读作 `_`），就从它的库根开始；其余算外部。路径一直走到最后一个模块文件，剩下的段是这个文件里的条目或内联模块，所以 `crate::Config` 解析到 `lib.rs`。
- **Rust 的 `#[path]` 和 `[lib] path`：** `#[path = "x_tests.rs"] mod tests;` 导入的是相对声明文件所在目录的那个文件；写在内联模块里时，内联模块名是路径里的目录（非 `mod.rs`、非 crate 根的文件，还要放在以文件名命名的目录下）。Cargo.toml 的 `[lib] path` 指定库根。经 `#[path]` 引入的文件，里面的 `super` 仍按普通模块文件算，所以常常是 `missing`；要算对得反查是谁引入了它，暂不做。
- **内联模块里的 `super`：** `mod tests { use super::*; }` 里的 `super` 是文件自己的模块。提取 import 时按所在内联模块的层数折算，`super` 记成 `self`，多出来的 `super` 才往上走。
- **引用在查询时解析，不入库：** 查"某个定义的引用"时，先取同名引用，再按 import 解析。好处是 import 或定义一变，下次查询自然就对，不用维护失效；代价是每翻一页都重新解析一遍。语言服务器也是这样做的。为了让每页够快，一次查询按名字批量读库：用到这个名字的文件里，只读能绑定它的 import（本地名等于这个名字或接收者的第一段，加上通配导入），一条 SQL 读完；定义按名字读，一个名字一条 SQL。只有顺着 import 走到的文件才读它的全部 import。别名只在以别名导入的文件里按别名查。耗时见 §11.5。
- **Rust 的 `Vec::new()` 不另判：** 曾考虑把 `Type::x()` 这种接收者是 prelude 类型的调用判为"指向别处"，没做：索引分不出 `Vec::new()` 和 `v.push()`（接收者都是一个词），要改提取再重建索引；泛型的 `T::new()` 可能就是调到我们的定义，会被误删；也不让查询更快。现在它们留在 `heuristic`（未经用户确认）。
- **一个名字指向哪里：** 本文件有同名 import 就顺着 import 走，没有再看本文件的定义（方法不算，方法要通过对象调用）；Python、Go、Rust 再看通配导入，Go 再看同一包目录里的其他文件。都没有就判定为"指向别处"，不算这个定义的引用。import 优先于本文件定义，是因为 TS、Rust 里两者同名编译不过，Python 里后写的赢，但 import 通常写在最前面、定义覆盖它的情况很少。
- **对象上的调用：** `this.x()`、`self.x()`、`Self::x()`、`cls.x()` 解析到本文件。`Foo.x()`、`ns.x()` 的 `Foo`、`ns` 是导入的类或模块时顺着 import 走，是本文件的类时看本文件里 `Foo` 有没有这个方法。其他接收者（变量、调用结果、`(await import()).x`）不推断类型，仍按同名匹配，标 `heuristic`。
- **只到文件，不到类：** 解析结果是"哪个文件里的定义"，不区分同一文件里两个类的同名方法。例如 `extensions/runtime.ts` 里两个类都有 `emit`，`this.emit()` 两个都算。要分清得按调用所在的类判断，暂不做。
- **别名：** `import { open as begin }` 之后的 `begin()` 也算 `open` 的引用。查询时先用 `aliases_of` 找出以别名导入这个名字的文件，只在这些文件里按别名查。schema 11 为此在 `imports(name)` 上加了只含别名导入的部分索引：TS 的每个 `import X from` 都算 `default` 的别名，没有索引时查 `default` 要扫全部 import。
- **结果顺序：** 解析到的（`syntactic`）在前，按路径、行、列排；没法解析的同名匹配（`heuristic`）在后。确定指向别处的同名引用不返回。`total` 是两者之和，另带 `resolved` 表示其中解析到的条数。
- **同一个方法，带不带 `path`：** `symbols.references` 带上定义所在文件的 `path` 时按 import 解析（下面几条），不带时按名字匹配、全部标 `heuristic`。不知道定义在哪个文件、或查外部库的名字时仍要按名字查，所以保留这种用法，但不另开方法。第 5 层先做成了单独的 `symbols.referencesTo`，产品代码里没有调用方，已合并。
- **地图的排序：** 文件按 import 边做 PageRank（阻尼 0.85，固定 50 轮，结果每次相同）；指向目录的边（Go 包、Python 命名空间包）平分给目录下直接的已索引文件。一个文件的顶层定义分摊这个文件的 rank，每个定义的权重是 1 加上按名字导入它的文件数；分数从高到低放进地图，第一个放不下的就停。分摊是为了不让一个大的类型文件占满地图（不分摊时 KodaX 的 `packages/llm/src/types.ts` 一个文件就占了 29 行）。同一个文件里同名的定义（重载）只列第一行。没有 import 解析的语言（Java、C++）各文件 rank 相同，地图基本按路径排，意义不大，暂不另想办法。
- **地图的格式：** 每个文件一行路径，下面每个定义缩进一行，内容是定义所在的源码行，去掉末尾的 `{`，超过 120 个字符截断。文件按路径排、定义按行号排，不按分数排，这样 rank 小幅变动不会打乱整张地图的顺序。文件在索引之后改过时，这个文件只写"种类 名字"，不读源码行，保证文本只取决于索引内容。不写"还有多少个定义"这类行，要看全部用 `file_outline`。
- **token 估算：** 和记忆索引同一个规则：ASCII 字符 4 个算 1 token，其他字符 1 个算 1 token。新增引擎方法 `workspace.map`，参数 `tokens` 默认 1,024。

- TS 基准没有回退：仍是 99.9% / 99.9%（TP 11,989、FP 7、FN 7）。

### 11.5 第 5 层结果（2026-11-25）

新增引擎方法 `symbols.referencesTo`（见 §11.2；之后并入 `symbols.references` 的 `path` 参数，下面的 `referencesTo` 都指带 `path` 的查询）。当时 schema 不变，仍是 10；之后为别名查询加索引升到 11。

KodaX 仓库，`npm run bench:repo-intel-v2-truth -- . --no-old`，抽 300 个函数和方法，调用方对照编译器真值（`findReferences`）：

| 来源 | 精确率 | 召回率 | TP | FP | FN |
|---|---|---|---|---|---|
| 同名匹配（`symbols.references`，阶段 1 记 34.4% / 97.5%） | 35.0% | 96.8% | 754 | 1,398 | 25 |
| `referencesTo` 只取 `syntactic` | 96.7% | 89.3% | 696 | 24 | 83 |
| `referencesTo` 全部（`syntactic` 加 `heuristic`） | 44.4% | 97.6% | 760 | 950 | 19 |

- 解析到的部分精确率 96.7%。全部结果的召回率 97.6%，不低于同名匹配，没有丢掉真调用方；同名匹配的误报从 1,398 条降到 950 条，其中 448 条被确定是"指向别处"排除掉。
- 只取 `syntactic` 的 24 条误报：大多是评测归属的问题（同一行里的内联回调如 `now`、`clock`、`execute`，以及真值没覆盖的 `.mjs`、`App.js`）；8 条是 `extensions/runtime.ts` 的 `this.emit`，见 §11.2"只到文件，不到类"。
- 只取 `syntactic` 漏掉的 83 条：泛型调用 `findAll<T>()` 在 L1 提取时就没记成引用（同名匹配也漏）；其余是变量上的方法调用、动态 import 的接收者、`(await import()).x`，按设计留给 `heuristic`。
- 别名支持加上后，`syntactic` 召回率从 88.6% 升到 89.3%，全部结果的召回率从 96.8% 升到 97.6%。
- import 边仍是 99.9% / 99.9%，没有回退。600 次调用方查询共 2,285 毫秒。
- codex（Rust，7,201 个文件）里查 `new`：同名 50,549 条，`referencesTo` 留下 22,608 条，其中解析到的 18 条（`client.rs`）或 2 条（`agent/types.rs`）。留下的大多是 `Vec::new()`、`String::new()` 这类：接收者是 Rust prelude 里的类型，文件里没有导入也没有定义，按"不知道"处理（见 §11.2）。

**单页耗时（2026-11-26）。** 每个仓库抽 200 个文件，查其中每个定义的引用第一页（50 条），索引已建好：

| 仓库 | 改前 p50 / p95 / p99 / 最慢（毫秒） | 改后 p50 / p95 / p99 / 最慢（毫秒） | 改后超过 200 毫秒 |
|---|---|---|---|
| KodaX（TS，3,737 个文件） | 3.8 / 12.5 / 44.6 / 112 | 0.5 / 2.6 / 6.9 / 16 | 0 |
| codex（Rust，7,201 个文件） | 9.5 / 41 / 505 / 582（56 次超过 200） | 0.4 / 3.2 / 85 / 204 | 2 |
| vscode（TS，16,737 个文件） | 38.9 / 52.9 / 114 / 178 | 0.5 / 12.5 / 76 / 140 | 0 |

- 改前每次解析一个文件都要读它的全部 import 和定义，codex 查 `new` 要读约 10 万行 import；查 `default` 时每个别名导入都扫一遍全部 import。改法见 §11.2：按名字批量读、别名加部分索引。没有加跨页缓存。
- 剩下的慢查询只有极常见的名字：codex 的 `new`（同名约 2.3 万条）约 200 毫秒，vscode 的 `add`、`get`（同名 4–6 万条）100–140 毫秒。p95 在三个仓库都远低于 50 毫秒。
- 改后调用方评测结果不变（96.7% / 89.3%，44.4% / 97.6%），import 边仍是 99.9% / 99.9%。
- 第一次在 codex 上测时，一页超过 9 分钟没出结果：顺着通配导入找名字时没有记住每个文件的结果，codex 成串的 `use super::*` 让查找按路径数指数增长。现在一次查询里每个文件、每个名字只找一次，import 成环时在环闭合处截断，不再靠 16 跳上限。修复后 KodaX 的调用方评测结果不变。

### 11.6 第 6 层结果（2026-11-25）

新增引擎方法 `workspace.map`（见 §11.2）。KodaX 仓库（3,737 个已索引文件），默认 1,024 token：32 个文件、52 个定义、1,018 token，生成一次 150–170 毫秒。

- 排在前面的是被大量导入的基础文件：`packages/llm/src/types.ts`（`KodaXMessage`、`KodaXToolDefinition` 等 10 个）、`packages/coding/src/types.ts`（`KodaXOptions`、`KodaXResult` 等 4 个）、`packages/agent/src/diagnostics.ts`、`staticText`、`createAgent`。
- 也排进了测试和评测的公共代码：`benchmark/harness/*`、`tests/runtime-fixture.ts`，因为很多测试导入它们。`src/sdk-runtime.ts` 这类大的核心文件导入它的文件少，没进地图。按 import 排序就是这样。要不要降低测试文件发出的边的权重，等第 9 层 eval 看地图对任务有没有帮助再定（未经用户确认）。


### 11.7 第 7 层结果（2026-11-26）

supervisor 增加 `query(root, method, params)`；每个 Run 拿到绑定了自己仓库根的查询服务（`RepoIntelQuery`），Host 在 `buildRunOptions` 里注入，调用方不能自带。新增工具 `find_symbol`、`file_outline`，只在绑定了索引时提供。

真实引擎在 KodaX 仓库上冒烟：查定义 1 毫秒；`resolveExecutionCwd` 带 `path` 查引用，34 处全部按 import 解析到，4 毫秒；`run` 有 172 个定义，按名字匹配引用 8 毫秒；`file_outline` 1 毫秒。

未经用户确认的实现选择：

- **子 Agent：** 和父 Agent 在同一个仓库根工作的子 Agent 继承索引；在自己 worktree 里的不继承，因为索引回答的是父仓库的文件，行号和内容会对不上。
- **建索引期间：** `find_symbol` 不给结果，只说明还在建、已索引多少文件，请用 grep 和 read。`file_outline` 照常回答：一个文件的大纲对这个文件是完整的，引擎会当场分析索引后改过的文件。
- **引用默认怎么查：** 名字只在一个文件里定义时，自动按那个文件做 import 解析；在多个文件里定义又没给 `path` 时，先列出定义，再按名字匹配列引用，并提示给 `path`。
- **路径的写法：** 结果里的路径相对当前工作目录，和 read、grep 一致；`path` 参数也按工作目录解析，仓库外的路径报错。
- **和其他仓库工具一致的地方：** 计为只读；仓库智能关闭时隐藏；结果在 microcompaction 中保留；计入"读了多少次还没定计划"的提示计数。
- **脚本工具里不加：** script pilot 的仓库工具列表没加这两个，等有用到再说。

### 11.8 第 8 层结果（2026-11-26）

地图放在 Managed Run Context 的仓库智能段里、概览之后，标题 `## Repository Map`，带两句说明（这些是被导入最多的文件和定义；大部分文件和定义没列出）。真实引擎在 KodaX 仓库上冒烟：整段仓库上下文 741 毫秒生成，地图约 1,000 token。

未经用户确认的实现选择：

- **什么时候带地图：** 和概览同时：新会话、计划任务或非简单任务。沿用现有 2 秒预算，超时就不带。地图在仓库智能段里，保留的会话只在这一段文字变了时重述，地图本身不变就不会引起重述。
- **索引没好时：** 不带地图，也不提示"地图稍后会有"。之后的 Run 只要带概览，就会带上地图。
- **说明里不写工具名：** 这一段也会出现在工具只能通过脚本调用的模式里，所以只说"大部分没列出"，不点名 `file_outline`、`find_symbol`。
- **引擎出错时：** 这一段不带地图、不报错。引擎故障由 supervisor 记日志，`find_symbol` 会说明为什么答不了。

### 11.9 第 9 层：提示词 eval 结果（2026-11-26）

`benchmark/repo-intel-nav-prompt.eval.ts`，用例和评分标准在 `benchmark/repo-intel-nav-prompt.cases.ts`。输入是真实 managed Runtime 的首个请求：Host 开着 v2 引擎，仓库是 packages/agent 的快照（402 个已索引文件）。候选组就是这个请求；对照组去掉 `find_symbol`、`file_outline` 和地图段，等于没有引擎时的请求。deepseek-flash、kimi-for-coding、glm-5.3-flash 各 3 次，共 90 次调用、122 万 token，没有报错和截断。

- **找调用方：** 9 次里 4 次用了 `find_symbol`（都同时跑了 grep），对照组全是 grep。没有一对比对照组差。
- **字符串搜索（守卫）：** 候选组 9 次都用 grep 搜环境变量，没有拿 `find_symbol` 去搜字符串。
- **大文件结构：** 候选组 9 次都用 `file_outline`；对照组整读文件、盲读一段或用 bash 列。
- **地图：** 候选组 9 次里 8 次第一步就搜地图里给出的 `NoteScope` 或 `memory-store/record.ts`，对照组 0 次；没有只看地图就作答的。
- **索引还在建：** 9 次都在同一次回复里改用 grep。
- **名字有多个定义：** 9 次里 8 次带上正确的 `path` 重查。

结论 recommend-ship，工具说明和地图措辞不改。§11.6 留下的问题定了：测试文件的边不降权，地图现在就能把模型引到对的代码。
