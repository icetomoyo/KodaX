## 2. 与 VISTA 的实质差异

### 2.1 方法位于任务级，工具只承担证据操作

VISTA 静态视觉 profile 在系统提示中组合任务约束和方法：先取得问题需要的证据，说明视图要解决什么，再检查它是否解决，随证据更新一个简短、可修订的理解。该 profile 只开放 `inspect`、`read_pixels`，并非把整个方法藏在一个工具里。来源：[profiles.py:27](C:/Works/PubProj/VISTA/src/vista/benchmarks/babyvision/profiles.py:27)、[profiles.py:56](C:/Works/PubProj/VISTA/src/vista/benchmarks/babyvision/profiles.py:56)、[profiles.py:69](C:/Works/PubProj/VISTA/src/vista/benchmarks/babyvision/profiles.py:69)。

这里的 system 是 VISTA 的 profile 字段：binding 将其写入 AGENTS.md，Codex backend 最终通过 `developerInstructions` 注入，不能把字段名直接当作所有 provider 的 wire role。来源：[binding.py:16](C:/Works/PubProj/VISTA/src/vista/backends/binding.py:16)、[runner.py:841](C:/Works/PubProj/VISTA/src/vista/backends/codex/runner.py:841)。

KodaX 上轮只把 325 bytes 指导放入 `visual_inspect.description`；G 请求仍有 57 个生产工具，system 未变。现有主合同的 visual-review 要求主要针对视觉创建、修改、评审，并不等于给所有视觉推理任务提供上述方法。来源：[visual-tools.ts:15](../../packages/agent/src/media/visual-tools.ts:15)、[compact-worker-contract.ts:31](../../packages/coding/src/prompts/compact-worker-contract.ts:31)、上轮执行记录。

**调整判断：需要修正“工具描述已经足够融合方法”的假设，但不能直接把位置差异认定为失败根因。** 先隔离位置因素，再考虑工具聚焦；不同时改位置、模型、工具数量、记忆及采样设置。

### 2.2 动态价值来自预测与反馈，而不是多看截图

VISTA 游戏指导明确要求动作前简述预期，动作后简述可见变化，包括意料之外的变化；保留简短、可修订的游戏理解。来源：[codex.md:1](C:/Works/PubProj/VISTA/src/vista/core/prompts/codex.md:1)。KodaX 已有 current/version/unknown 合同及动作后观察，可以承载这种有目的的交互，但本轮尚无在线行为证据证明模型会据反馈修订计划。来源：[visual-environment.ts:90](../../packages/coding/src/media/visual-environment.ts:90)、[visual-environment.ts:114](../../packages/coding/src/media/visual-environment.ts:114)。

建议复用现有消息、工具 question/label 与压缩摘要，表达“待判断问题、相关观察、结论和未决项”；只要求短证据说明，不要求冗长逐步推理。不照搬新 GUIDE.md/WORKING.md 文件体系，不引入第二个规划模型或强制每轮取证。

### 2.3 不能把外部存图等同于 token 节省

KodaX microcompaction 明确保留图片块，包括工具结果内的图片。VISTA runtime 的图片计数与工具图片上限本身也不能证明模型上下文中的旧图已被淘汰。来源：[microcompaction.ts:119](../../packages/agent/src/session-lineage/compaction/microcompaction.ts:119)、[runtime.py:322](C:/Works/PubProj/VISTA/src/vista/core/runtime.py:322)、[runtime.py:445](C:/Works/PubProj/VISTA/src/vista/core/runtime.py:445)。

因此当前没有依据承诺“保存历史后自动更省 token”。需要观察生产请求是否重复携带大图、工具合同如何逐轮累计；证据裁剪、按需装配、历史摘要分别作为后续优化变量。严格 8-bit RGBA、透明度及精度合同继续保留，不为模仿 VISTA 改为有损像素值。

VISTA 的 checkpoint 路径确实可以新开模型会话，并以当前观察、最近动作、历史引用与笔记恢复；这有别于每轮自动删图，外部历史仍可供 inspect。BabyVision 又采用 native compaction，不应把游戏恢复策略泛化到所有 profile。来源：[session.py:304](C:/Works/PubProj/VISTA/src/vista/backends/session.py:304)、[binding.py:59](C:/Works/PubProj/VISTA/src/vista/backends/binding.py:59)、[profiles.py:72](C:/Works/PubProj/VISTA/src/vista/benchmarks/babyvision/profiles.py:72)。

## 3. 建议的融合方式与先后顺序

1. **先移动方法，不增加方法长度。** 将上轮同一段指导从 inspect 描述移动到现有任务提示 section，工具保留原操作合同。用同一模型、输入、完整工具集合进行位置消融；新旧两边都只出现一次方法文本。源码接缝可复用 [builder.ts:27](../../packages/coding/src/prompts/builder.ts:27) 与 capability-context sections；具体所有入口是否覆盖必须先用请求快照确认，不能仅验证 Coding SA 就宣布 SDK/AMA 全覆盖。
2. **再验证方法本身。** 若位置变化仍不能解释结果，单独试验更清晰的短方法：“找到影响答案的未决点；必要时选择最小相关区域/历史时刻；依据返回内容更新判断；不能验证的事实明确保留；证据充分则作答。”动作任务另外强调预期与实际反馈。不得同时换模型、增加强制调用或向用户问题泄漏选区。
3. **生产装配按任务需要，不能按 owner 存在一刀切。** owner 表示有能力，不表示任务需要视觉。普通代码任务不应长期携带额外方法；历史图查询又不能因为当前没有新图而漏掉方法。使用现有输入接纳、历史引用及活动视觉任务上下文设计最小触发条件，先离线覆盖“有新图、只问历史图、压缩恢复、任务结束后转普通代码”。不新增模型分类器或全局配置。该条件尚未实现和验证。
4. **有行为收益后再做成本优化。** 工具聚焦可借鉴 VISTA，但生产任务有正常 read/shell 等需求，不能为了胜出删掉基线工具。合同按需暴露与图片保留策略分别测，保护已有精度、恢复、容量、动作失效合同。不要在第一轮同时收窄 57 个工具，否则无法知道改进来自哪里。

此顺序保留 P0–P6 工程成果，也允许最后得出“只在特定视觉任务启用”或“保留底层能力、撤回没有价值的指导”的结论，不以已投入工作量作为采用理由。

## 4. 重做验证问题，而非只重跑 A/B/D

旧 A 固定拓扑，只扰动标签；它混合局部辨认、整图连通推理与旧答锚定，已经用于调试，保留为回归反例，不算新的泛化样本。B 的三张具名原图始终可读且用户明确要求比较历史；D 是非视觉控制。源码：[task-fixtures.ts:16](../../benchmark/visual-harness/task-fixtures.ts:16)、[task-fixtures.ts:37](../../benchmark/visual-harness/task-fixtures.ts:37)、[task-fixtures.ts:71](../../benchmark/visual-harness/task-fixtures.ts:71)。VISTA 本身有静态视觉任务，不能把旧 A 失败简单解释为“接线题不是 VISTA 场景”。

新任务应有实际交付物，以及**一个可见证据变化便会改变正确答案的反事实版本**。真值从独立的状态/布局定义生成或人工逐项核验，不从候选答案反推，也不在文件名、文本日志或工具结果中泄漏。首先选择与 KodaX 更接近的产品面板/渲染诊断，不引入 ARC 或完整桌面。

| 任务 | 用户实际要完成什么 | 关键对照及成功依据 |
| --- | --- | --- |
| 局部证据诊断，优先 | 从实际渲染的密集设置/状态面板定位一处导致任务失败的设置，给出正确修正 | 两图只改变关键状态，正确诊断随之变化；应选对区域并据证据给出正确修正，不能只算“用了 inspect” |
| 历史状态诊断，第二批 | 解释某次操作后异常从何时出现，区分目标时刻与后来无关操作 | 给相同历史事件与原图访问权，不直接指明要比较哪两图；既要选对时刻，也要正确解释证据能证明和不能证明的内容 |
| 动态消歧，第二批 | 在现有受限视觉宿主中完成一个小目标；初始画面不足以区分两种状态，需一次合法观察/动作 | 相同外观、不同后续反馈，正确下一步不同；验证根据反馈改变动作、在完成/未知时正确停止，不能把固定动作序列当成功 |
| 克制与成本控制 | 普通配置修复；另有一张细节已清晰的简单图片问题 | 任务正确且不做无用取证；D 留作负对照，不能充当视觉收益证据 |

历史任务不得故意删掉基线可读的文件、藏起原图或强迫其忘记来制造胜出。若测真实瞬时输入的保留/恢复，必须通过相同用户输入过程建立历史，保留基线原有行为，单列为“生命周期能力差异”；不能据此声称同等信息下推理更聪明。动态宿主若 B0 没有同等合法操作接口，先做当前候选的“有/无方法”比较，不假装是整套框架公平对比。

## 5. 每一批实验回答一个可决策的问题

### 批次 0：离线有效性检查，不花模型 token

冻结图片、反事实真值、生产请求字节与真实工具反馈；核对正常视图、crop、坐标和颜色在目标序列化链路中一致。用回放检查失败/无效工具提案、容量不足、stale/unknown、取消的实际处理，不伪造工具成功。检查全文及路径无真值泄漏。准备 quality-only 证据包，不能提前显示 token 或 arm 映射。

这些机制问题能由 Layer 1 回答。模型是否主动选证、是否利用证据改判、是否做多余工作不能由单测回答，才进入下一层。

### 批次 1：证据本身有没有决策价值

新建一个未用于调词的局部诊断任务及其反事实版本。每个版本各做“全图”与“全图 + Host 预先核验的相关 crop”，共 **4 个单响应样本**。同一问题、无旧错答、无正确答案提示；两条件原图相同。它只测给到证据后的使用能力，不测自主取证，也不把 oracle crop 条件当成生产候选。

- 全图易错、增加相关局部后能给出正确且随反事实变化的答案：此任务有验证取证价值的理由。
- 两条件都正确：该题没有显示改善空间；保留结果，可作为克制对照，不能报提升。
- 两条件仍错：该诊断不能把“有工具但不用”当唯一原因；复核图片/任务歧义、证据充分性和语义整合，保留失败。
- 一次差异不足以确立稳定提升；可在解释后冻结第二个独立布局复验，不能不断挑题直到候选获胜。校准题及所有被换掉的题公开保留。

这四次只能初筛。若出现相关 crop 条件改善、要进一步归因为“相关证据”，可另冻结两个等尺寸无关 crop 条件，排除仅增加图片/注意力提示的解释；不在看到输出后悄悄追加到原批次。更接近生产任务的持出布局仍须独立保留。

### 批次 2：模型能否主动选择证据并使用反馈

用一个新的局部诊断反事实对，比较 **C-tool（当前方法位于工具描述）与 C-task（同文案移至任务 section）**，每个版本每 arm 一次，每次最多三响应，总计最多 **12 次请求**。这是位置消融，不是与 B0 的完整改造比较。

固定响应流程：R1 给原图和正常任务 → 若有合法取证提案，执行真实生产工具并在 R2 返回结果 → 允许一次补充取证，R3 给其结果并记录最终答案或未完成。提前正确作答可结束；错误直答也按事实结束，不额外追加“请调用工具”来救场。无效提案返回真实错误，占用本来额度。每响应最多两个只读取证调用，整格最多四个；不许环境动作、child、重试或额外 judge。正常 read 等既有路径仍按冻结权限可用并记账，不能因没有用 visual 工具就判失败。

评审依次记录：最终任务是否完成且答案有依据；关键事实是否随反事实变化；是否找到相关区域/时刻；反馈是否进入最终判断；若出现原错答，是否被纠正；是否存在过度自信、无用调用或无根据的额外结论。承认未核实优于编造，但不等于完成任务。若前后始终正确，则只能证明取证/使用，不能报“纠错”。

旧错答挑战另列 anchored 条件，不能与 fresh 混算；必须两 arm 注入相同错误及复核消息。先不要铺开多模型、多提示词矩阵。批次 1 语义失败不自动取消仍有独立价值的批次 2；每批解释究竟能识别哪种问题，再决定追加范围。

### 批次 3：有限任务的真实收益和总开销

方法收敛后，用上述历史/动态小任务的固定、最多三响应交互，检验完整小目标是否实现；每一步的工具反馈按实际选择与冻结状态机产生，不给“标准答案反馈”。先完成一组配对、解释后再追加另一任务。比较整个改造时用 B0 对新候选；比较提示词时用同一工程候选的提示词变体，账目与结论分开。

最后至多三个 case 走真实 Runtime 的 Layer 3.5 smoke，包括正常辅助工作结算和原 D 控制；仅报告集成完成情况与观察到的成本，不把自由循环的差异当作 prompt 因果证据或总体优劣结论。符合 [EVAL_GUIDELINES](../../benchmark/EVAL_GUIDELINES.md) 的比较依据来自上面的受控任务，smoke 用于查真实集成是否推翻该判断。

## 6. 全程 token 怎么比较才有意义

每个配对先锁定答案/动作质量判断，再揭示成本；工具名可能暴露 arm 时如实标部分盲化。不同任务、fresh/anchored、不同模型不混成一个成功率。pilot 每格一次仅用于有效性与方向判断，若形成采用建议，需要在独立输入或必要重复上复验，保留全部反例与方差，不能把单样本写成稳定收益。

记录 API input/output、缓存字段、主调用、压缩、后台评审、失败/修复、工具耗时、独立图片数与每次实际发送次数/尺寸/hash、用户完成与全部结算耗时。缓存 token 属于 input，不重复相加；图片 token 若 API 未拆分则标 unknown，不能按本地估算冒充。账单/订阅分摊与 token 分列。

完整任务口径从共同初始状态开始，包含为该任务建立历史、压缩、取证、动作、验证与正常辅助工作的全部调用。若现实里复用已有历史，分别给出“含历史建立”和“已有历史上的新增任务”两种账目，不能只报对候选有利的一种。离线 fixture 构建时间独列，不算作省掉的模型 token。

| 观察 | 应采取的方向 |
| --- | --- |
| 同质量，调用或总 token 更少 | 保留有效机制，复验节省是否稳定 |
| 能完成原本失败的任务，但 token 更高 | 先量化具体收益及代价，再考虑按任务启用与成本优化，不立即否决 |
| 质量没有改善，token 更高 | 不继续扩能力；定位固定合同、重复图片或冗余调用，或撤回无益方法 |
| 看似省 token，但早退/未完成 | 记为失败成本，不称效率提升 |
| 更多工具调用却答案无改善 | 不是成功；检查证据相关性与使用过程 |
