# Issues 449 and 450: rejected images and a session the provider keeps rejecting

Fixed after `v0.7.97-rc.4`, unreleased. Automated tests cover the image
steps with stubbed providers and the recovery mark in the Host and the REPL.
Only real providers prove the pixel limits, so run these steps before release.

## Contract

- A request scales any image over 8000 px on a side. The file and the
  transcript keep the original.
- When a provider rejects a request with 400, 413 or 422 and the error is not
  about the account, images that model never accepted are retried at 2000 px
  and then omitted. The error text does not need to mention images.
- Images the model accepted earlier keep their bytes. Unit tests cover this.
- When the same rejection from the same provider and model ends two Runs of a
  session in a row, the REPL suggests `/recover` and the Host reports
  `failureDetail.historyRejected: true`. Nothing changes automatically.

## Setup

- A KodaX build that contains these fixes.
- A DeepSeek key with `deepseek-flash`, which accepts at most 8192 px per side.
- A tall PNG, for example a 520x9800 full-page screenshot. Keep its path.

## Cases

### 1. Tall screenshot (the reported case)

1. Start the REPL with `deepseek-flash` in a scratch project.
2. Ask: "Read `<path>` and describe the page."

Expected: the Run succeeds. The model can say that the image was scaled from
520x9800. No 400 appears.

### 2. Session that held the screenshot before the fix

1. With a build from before this fix, repeat case 1 so that the Run fails
   with the 8192 px 400. Send one more message, which also fails.
2. Switch to the fixed build and continue the same session (`kodax -c` or
   `/load`).

Expected: the next message succeeds. The rejected image is scaled, or omitted
with the provider's reason, and the session can continue.

### 3. Recovery offer after a repeated rejection

A rejected history is hard to produce on purpose. A model id that the
provider answers with 400 stands in for it. It only proves the offer, not
the cause.

1. In a session with at least one answered turn, set a model id that the
   provider rejects with HTTP 400. Confirm the first failure shows 400.
2. Send one message. It fails without the `/recover` hint.
3. Send another message. It fails the same way.

Expected: the second failure shows "Run /recover [prompt] to continue in a
fresh session from safe memory." `/recover` creates a new session from a
summary. With Space or another SDK client, the second failed Run has
`failureDetail.historyRejected: true`, also after the Host restarts.

## Record

For each case, record the provider and model, the image size, the Run result,
and for case 3 the `failureDetail` of both failed Runs.
