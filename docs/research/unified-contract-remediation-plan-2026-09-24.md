# 统一契约面：整改与验收方案

日期：2026-09-24。设计讨论基线：`fa2db204d12111e4d1c32e83a3594dc3f4870423`；主线比较点：`c447c0f3`。

状态：2026-09-24 形成方案；2026-09-26 用户授权后开始实施和端到端验证。此文保留设计决策，实际验证结果另记回归指南。
证据与问题编号见 [设计对照审计](product-contract-design-audit-2026-09-24.md)。
设计依据为 [CLIENT_CONTRACT](../CLIENT_CONTRACT.md) 和 [FEATURE_298](../features/v0.7.97.md)，尤其既有 Testing Decisions 的 S1。

## 结论与责任

保留“Host 持有事实，Client 提交意图并消费事实”的架构。当前 9 项已确认问题主要是这个边界没有落实：
Host 把 REPL 展示转换当成原文，多个读取面各自解释同一事实，消费者把缓存回写成设置，异步错误只通知当时的等待者。
Learning/Workflow 的观察终止与恢复责任还需要补充公开契约。不是把 API 名称统一就已经完成了统一契约。

上一轮修复及验证范围过窄：383 项测试与 48 项 PTY 是输出专项证据，不是完整契约验收。
排序测试仍有页内锚点，未覆盖真实字节预算产生的无共同锚页；保存测试只覆盖等待过程中失败；
工具状态未跨公开 history 比较；ACP 未串联计划批准和下一轮；订阅未覆盖首次 next 前失败。
因此上一轮排序修复不完整，不能继续用通过数量证明这一类问题已经解决。

本次改为：冻结少量产品不变量，按真实生命周期验证不同接口是否给出同一事实；先使已知反例失败，再逐片修复，最后对固定提交验收。
优先复用已有 Session 存储、来源和测试设施，不承诺零缺陷。正确性优先于改动大小：若反例证明信息或接口表达不足，补充必要机制；不把“不新增日志/状态机/API”当作硬性约束。

## 子 Agent 讨论后的取舍

三个 Agent 分别负责事实投影、生命周期、独立验收，并互相质询。以下不是三份并列备选，而是收敛后的方案。

| 讨论点 | 最终选择 | 收缩理由 |
| --- | --- | --- |
| 共享投影放入 coding 公共包？ | 先在 `src` 内部收敛 | 三个实际调用方都在 Host，暂不扩包 API，不搬整套 REPL 恢复逻辑 |
| 新建永久全序位置？ | 保留现有来源上下文，只派生当前 revision 内的位置 | page index 跨压缩/分支不稳定；身份不等于顺序，不能把临时下标落盘 |
| 所有 UI-only 项加新锚？ | 本轮不预先添加 | 当前契约明确分轮；F04 已有 callId。仅有反例证明既有顺序承诺需要额外信息时才加窄字段 |
| 保存失败新增代次协议？ | 复用当前串行完整 checkpoint writer，显式保存失败状态 | 后继成功必须覆盖同 Session 失败内容；不为目前的串行写入引入另一套提交协议 |
| 所有订阅自动重连？ | Session.observe 保持现有行为；Learning/Workflow 明确终止，由消费者重建 | 没有事件无损承诺，重连以快照收敛，不重放 mutation |
| 并发 next 拒绝第二个？ | 最小 FIFO 等待队列 | 避免新调用限制，也避免单唤醒槽覆盖等待者；不做通用流框架 |

## 必须同时成立的不变量

1. **原文只有一个权威来源。** 已提交正文、工具参数、结果状态取 canonical；checkpoint 只补显示元数据和未提交内容。预览裁剪只发生在展示出口，不能回流为“全文”。
2. **身份决定归属，来源决定顺序。** 新身份数据不按文本猜测来源或去重；canonical 遵守 conversation 与内容块顺序。不同读取面的 itemId 可属于不同命名空间，不要求互换。
3. **终态与保存、观察状态分开。** Run completed 不等于显示快照已保存；断连不等于任务完成；保存失败不能因 Promise 已清空而变成成功。
4. **Host 校验后才消费意图。** 无效答案不改变 pending；只有首个有效答案消费请求。客户端缓存不能在普通 prompt 时覆盖 Host 设置。
5. **每个异步等待都有可观察的结局。** 订阅失败、主动关闭及迟到握手有确定行为，不留下悬挂的 next，也不复活已结束订阅。
6. **恢复仍遵守相同规则。** live、提交、分页、重启不是另一套内容解释器；不能用丢失原文、重排结果或隐式重试 mutation 换取恢复成功。

## 实现边界

### A. Host 统一事实投影与正文读取（F01、F02、F04、F05）

- 在 `src` 收敛窄 canonical projection，供 `session-view`、`client-history` 及 `readItem` 复用原文、工具参数、明确状态和来源定位。不新增对外 facade。
- 从 canonical tool_use/tool_result 读取完整数据。显式 cancelled/is_error 优先于旧文本启发式；真实 inputId 与可信来源标记优先于内部提示词的关键词。
- REPL sanitizer、折叠和格式化留在展示层；无身份旧数据的兼容规则单独保留，不能污染新数据路径。
- 保留 conversation page 既有 index、boundaryId、auditEntryIds 上下文。callId/outputId 映射到当前 revision 的来源位置，分页合并不依赖页内共同锚。
- 位置只在当前 revision 生效，压缩/分支变化使缓存失效。现有 cache prepare 可派生有界保留项的定位引用；冷缓存沿用既有构建，热补读不得重新扫描整段历史正文。
- 顺序承诺固定为 canonical 源顺序、可定位显示项的相邻关系，以及现有 afterInputId 分轮规则。旧无来源 UI-only 按文档化兼容处理，不按时间或正文编造精确全序。
- 若实施中出现两条合法轨迹落盘事实相同但违反既有顺序承诺，先固化反例，再为现有 uiHistory 增补必要来源身份；不预先造永久顺序号或新日志。
- 三个现有全文拼接校验器可以收敛为窄共享 reader；统一连续 offset、总长度和 revision 检查。UTF-16 字符 offset 与 UTF-8 分页预算不可混淆。

### B. 保存屏障与交互校验（F03、F06）

- `SessionViewOwner` 按 Session 保存“存在未恢复故障”及原异常，不能仅用异常值 truthiness 判断，`reject(undefined)` 也算失败。
- flush 等待在途写入后还检查故障；既有会话读取、history refresh、fork/recover、close 的屏障都使用同一规则，不能仅在 persisting 存在时调用。
- 读取、记录诊断或捕获异常都不清除故障。只有同 Session 的后继完整 checkpoint 成功覆盖失败内容，或成功删除该 Session，才释放对应故障。
- close 等全部 Session 的 flush 结算，清理资源并报告失败；一处失败不能跳过其他 Session 的清理。不把保存错误伪装为模型执行失败。
- Runtime 复用现有同步“校验→settlePending”边界，将按 kind 的形状校验改为按当前 request 的约束校验：选择值、customInput、唯一选项数/min/max、多题键集合。
- 无效答复返回现有 typed error，pending 不变；取消仍按取消语义处理，不受 minSelections 阻挡。超时默认复用已有合法性判断，不新增锁或重复规则。

### C. ACP 只提交明确意图（F08、F09）

- 初始化与显式 setSessionMode 才提交相应设置意图；普通 prompt 不回写整包本地缓存。构造器补出的默认值不能被当作用户意图。
- 先消费 Host view.settings，再计算 effort；本轮明确 override 沿现有设置并发规则处理。设置失败不能预先把本地缓存标为成功。
- Host 设置变化更新 ACP 显示和 current_mode_update，不写回。另一个 Client 的设置与计划批准后的模式必须在下一轮继续有效。
- 计划批准内容来自完整 options.plan；不能从通用工具 inputPreview 推造完整计划。批准及模式切换仍由 Host 裁定。

### D. 可观察的订阅生命周期（F07 及契约缺口）

- Workflow 保留 subscribe/close，公开握手 ready，增加可选 onError 通知握手后失败/断连；主动 close 由调用者已知，不新增状态枚举。
- Learning 暴露 ready 与 iterator。ready 仅代表订阅注册完成，不表示快照或列表已同步。
- 早失败须使 ready、当前与之后的 next 失败；不能只调用当时可能尚不存在的 reject 回调。
- next 等待者按 FIFO，一条事件交给一个等待者。return 幂等，清空缓冲并令所有等待者 done；failure 清空缓冲并令所有等待者 reject，之后保持失败直到显式 return 关闭。
- return 先发生时迟到握手只做清理；failure 先发生时已失败的等待不能被 return 改写成成功。结束后的通知不得复活订阅。
- Learning/Workflow 断连终止观察，生产消费者显示失败并负责重建；不停止 Run、不自动重放 mutation。Session.observe 沿用已有恢复语义，不强改成同一个机制。
- 重建先订阅并等待 ready，再读快照；快照期间的通知缓冲为再次刷新信号，有 revision 时按既有 revision 去重。Learning 的计数 snapshot 不能代替 list/get 的实际内容恢复。
- Host 已有 subscribe 回执与 transport lifecycle，预计不需新增 RPC，Host productClient v1 保留。新 SDK 行为保证不等于旧 SDK 自动获得保证；必需 ready 会影响自实现 Client 的 TS 结构，必须同步适配与迁移说明。
- 旧 Host 线协议兼容验证是门禁。若实现发现必须依赖新 Host 字段或能力，必须修订能力协商决策，不能继续沿用“纯 SDK 修复”的结论。

## 有限验收矩阵

主接缝复用已确定的 S1：两个 Product Client → 真实 IPC Host，临时 profile 与真实持久化，确定性 Provider/工具。
Host 与 Client 使用不同 home/profile，避免共享文件掩盖旁路。细小时序可在生产 iterator/owner 上用受控依赖验证，但不能用全 stub 替代公共闭环。

| 事实 | 必选变化 | 核验面 |
| --- | --- | --- |
| 输入、回答、工具原文 | live→提交→有/无 checkpoint 重开 | observe、readItem、history/entry |
| 工具状态 | success/error/cancelled，正文含 `[Error]` | 当前视图与公开历史 |
| 来源顺序 | 条数/字节分页，有锚/零锚，压缩/修订 | 恢复视图、历史、窗口外补读 |
| 保存故障 | 等待前/中失败，失败后覆盖成功 | 既有公开读取屏障、关闭 |
| 问答、计划、设置 | 无效→有效→重复/竞争，取消，下一轮 | respond、ACP 协议、第二 Client |
| 订阅 | 早失败、多 next、return、断连、快照期间变化 | SDK、生产绑定、重建后事实 |

期望值直接来自 fixture 原始字串、显式状态与操作顺序，禁止调用被测 projection/restore helper 生成期望。
跨面按 inputId/outputId/callId 或 fixture 来源映射比较事实，不要求 itemId 相同。
固定边界集改变 chunk 切分、UTF-8 页预算、CJK/emoji、重复快照和保存先后，正文与可证明顺序必须不变。

专项之外，复核已有运行/停止回执、队列撤回与 steer/redirect、审批、设置配置/MCP、Learning/workflow、命令/Skill、恢复的公开入口覆盖。
每域复用一条已有真实 Host 正常闭环和最相关失败/恢复证据；缺失才补，不为每个 UI 重复全套业务测试。
这样检查的是统一契约既有能力边界，不把这次方案悄悄扩成新功能开发。

Ink/classic 的 PTY 只承担渲染、长输出、输入/停止、重挂接和展开/滚动差异；ACP 另走真实协议序列。
用户报告的普通模式滚动 Issue 342 仍待复现：保存环境、按键与窗口条件继续跟踪，不能因输出测试通过就关闭。
原 Session 丢失的未落盘后缀不能靠修复重建，不拿恢复出的残片冒充完整答案。

## 防止同类回归与完成条件

静态护栏只守三个已确认边界：Host 事实投影不依赖 REPL 裁剪/清洗；产品客户端不读取 canonical 存储、不隐式回写设置；全文分页校验归口后不再复制。
优先现有 import/lint 规则和有限模块约束，设置写入意图仍由行为测试验证，不能指望全文正则证明语义。

每个契约不变量在验收表中有 owner、公开入口测试和负向序列。以后主线合并或迁移触及该边界，就重跑对应矩阵行及消费者薄层测试；接口清单只能证明入口存在，不能代替行为证据。

本批完成必须同时满足：

1. F01–F09 各有基线业务断言 RED 与候选 GREEN；生命周期缺口落实到类型、文档和真实消费者。
2. 上述矩阵有实测证据，新增测试的失败不能仅是装配错误或超时噪声；不靠增加重试、削弱断言过门禁。
3. 相关原有测试、build/typecheck、PTY 与发行构建的 Client 入口检查通过；预存失败需基线对照，不能自动归为无关。
4. 固定最终候选 SHA 和构建产物，独立 Standards/Spec 审查检查整条受影响调用链，不仅检查单文件局部差异；无未处置的已确认契约缺陷。
5. 明列未证实问题和能力限制。Issue 342 未复现时明确保留，不能声称用户报告的所有症状已解决；既有主线旧债另记，不隐匿也不无限扩本批。

冻结范围后，新的反例若破坏这些不变量就回到对应切片；新能力或独立旧债单独记录。审查后若修改代码，相关证据在新 SHA 上重验。
以这些可检查条件结束整改，不以“再审一轮没有发现”结束，也不以不断扩大审查范围替代完成。
