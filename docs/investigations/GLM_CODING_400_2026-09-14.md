## 结论

**客户补充的会话分析与独立真实接口复现高度一致：坏图片进入工具历史后持续
返回 400。现有证据支持无效图片重放是本次故障原因，不支持归因于 Anthropic 排序改动。**
最初只有截图，合成复现不足以认定客户根因；随后用户转来包含具体图片、时间线和
上游错误的客户分析，补上了对应关系。原始 JSONL/JPEG 未在本机独立检查，下面明确
区分客户转述证据与本机实测。

当前排序和旧排序对照都返回 200；真实 SDK 流式调用、真实模型发出的工具调用、
回填合成模板、修改金额，在两家接口也均成功。自动思考模式的三轮请求都实际产生
了思考块，因此不是只测了无思考的文本对话。

## 已知客户现象与调查边界

- Space `v0.1.46-beta.2`，`glm-5.3-flash`，自动思考，Provider 可能是两家 Coding 之一。
- 模型表示先分析 `.doc` 模板的页眉、字体、页边距；界面记录 16 个命令后失败。
- 用户随后发送继续、修改金额、继续，仍失败；首次失败早于金额修改。
- 展开详情为 `upstream / transport / upstream_client_error / HTTP 400`，没有具体原因。
- `1.5M` 是累计用量，不能作为单次请求超限证据。
- 本调查只发送合成文本、工具结果和测试图片，没有上传客户文件或对话。

### 客户补充分析（用户转述，2026-09-14）

分析引用会话 `20260914_094401_es887b8d024364.jsonl`：09:49 首份报价 docx
已完成；约 09:50 开始处理 `2025版协议2页中盾页眉.doc`；09:56:12 用 `read`
查看提取出的 `img/img_6433.jpg` 后，请求开始持续失败。kimi-code 报
`failed to decode image: invalid or unsupported image format`，切换 zhipu-coding
重试三次仍报 `1210 / 图片输入格式/解析错误`。之后继续及金额修改都未执行。

该分析称 `img_6433.jpg` 有 JFIF/EXIF 头，却没有 SOF 帧数据，PIL 无法识别；
另外两张 `img_11609.jpg`、`img_6765.jpg` 为正常 160×46 Baseline JPEG。
这比本机“PNG 扩展名配文本字节”的样本更贴近实际截断文件：**仅检查扩展名、
MIME 或文件头不足以修复，必须验证图片能够解码。** 该具体 JPEG 尚未在本机复现。

客户所述坏图读取、跨通道解析错误、后续请求持续失败，与本机 SDK 的
`400 → 400 → 仅修复图片字节后成功` 因果对照吻合。历史保存图片引用并在请求时
重新读取；并非会话不可逆地损坏。修复应覆盖已存在的历史附件，不能只防止新坏图进入。

## 排序改动的实际范围

`b25c5142`（2026-09-11）修改了共用的
[`anthropic.ts`](../../packages/llm/src/providers/anthropic.ts)：

1. assistant 的 text/reasoning 按相对顺序输出，所有 `tool_use` 移到后面。
   因此它不是任意输入的完全原序透传；典型内部历史从旧的
   `thinking → tool_use → text` 变成 `thinking → text → tool_use`。
2. user 保持 `tool_result` 在前；同一 assistant 到下一个 assistant 之间的结果合并。
3. 未配对调用保留并合成中断结果；外来、重复结果移除。

两家 Coding 的类都继承这个实现，所以用户的怀疑有真实代码路径依据。
但仅改变 assistant 块顺序的真实接口对照，两家各一次，全部返回 200。
这只降低“排序本身”的嫌疑，不能排除所有特殊历史、长上下文或网关版本的影响。

## 稳定复现：工具图片使会话持续失败

最终复现经过真实 `toolRead()`、运行层清理函数、Provider 序列化、Anthropic SDK、
真实服务器以及 KodaX 错误包装。没有替换服务器的 400 响应。
未启动 Space/Electron 或共享 daemon，也未运行客户的实际 Word 渲染脚本。

1. 创建 `.png` 文件，内容为合成的“文档渲染失败”文本。
2. `toolRead()` 按扩展名和大小把它返回为 `image/png` 工具结果。
3. 使用匹配工具 ID、包含真实图片路径的调用和结果构建历史，发起下一轮请求。
4. 追加 `Continue.` 再发。
5. **保持消息历史和顺序不变，只将同一路径的文件字节改为有效 PNG**，再次发起请求。

| 阶段 | zhipu-coding | zai-coding |
|---|---:|---:|
| 首次坏图片请求 | 400 / 1210 | 400 / 1210 |
| 追加继续 | 400 / 1210 | 400 / 1210 |
| 仅修复文件字节 | 200 / OK | 200 / OK |

错误正文：`[1210][图片输入格式/解析错误][request_id]`。
最终实验每家两次相同失败、一次恢复；此前矩阵也每家观察到两次同类失败。
首次 SDK pilot 也得到相同结果，其产物单独保留；最终版本将历史调用参数中的
路径对齐实际 `toolRead()` 路径，避免用不同路径的工具结果描述完整调用链。

### 原因与历史归属

- [`read.ts`](../../packages/coding/src/tools/read.ts) 的图片分支（349 行起）只检查
  扩展名和大小，没有验证图片内容；该逻辑可追溯至 `c76df9600`（2026-05-20）。
- [`image-serialization.ts`](../../packages/llm/src/providers/image-serialization.ts)
  直接读取文件并 base64 编码；只对文件不存在提供降级，不处理文件存在但无效。
- 每次发请求都会重新读取历史中的图片路径。因此追加 query 不会去掉坏图片，
  排序和工具配对修复也不会修复图片字节。
- 额外检查了运行层 `lowerProviderMessages` 和 `tool-result-policy.ts`：前者只处理
  ephemeral suffix，后者保留图片项并限制文本/容量，都没有提供图片解码验证。
- 这条失败链路早于 `b25c5142`，不是该排序提交新引入的缺陷。

## 为什么丢失具体错误信息

真实 SDK 抛出的错误消息仍含 `1210` 和图片解析原因，但包装后的 metadata 只有
`stage / httpStatus / requestId`，没有 `upstreamCode`。

[`base.ts`](../../packages/llm/src/providers/base.ts) 的 `extractErrorCode` 只读直接
`code` 和 `cause`。Anthropic SDK 将完整响应放在 `APIError.error`，本次上游 code
位于 `APIError.error.error.code`，不会被该函数提取。

[`run-substrate.ts`](../../packages/coding/src/agent-runtime/run-substrate.ts) 的
`terminalProviderFailureMessage` 和 [`sdk-runtime.ts`](../../src/sdk-runtime.ts) 的
`classifyRuntimeResponseFailure` / `runtimeFailurePublicMessage` 再将此类 400 投影为
`upstream_client_error` 和 `Provider rejected the request.`。这与截图的字段组合一致，
但该组合也可能对应其他 400，不能据此倒推出客户的具体错误。

## 排序相关的两个其他缺口

离线对比 `b25c5142^` 与当前 Provider，并通过运行层真实清理函数验证：

1. `validateAndFixToolHistory` 仍只认可紧邻的消息配对。若工具结果分散在多个 user
   消息中，先清理会删除真实调用/结果。当前 Provider 直接接收原历史能保留结果，
   但经过清理后它们已经消失；HTTP 200 测试无法发现这种信息损失。
   这一问题在旧版清理链路也存在，不能称为排序提交导致的新回归。
2. `b25c5142` 增强了 `classifyError` 的工具配对错误识别，但运行中的
   `llm-adapter.ts:1002` 调用 `classifyResilienceError`。同一个配对错误在前者是
   可重试，在后者是 `non_retryable_provider_error`。修复旧分类器不等于修复当前
   恢复链路。是否应该自动修复需有特定历史契约，不能对所有 400 无条件重试。

这两点值得另行修复，但本次矩阵中没有因此产生真实 GLM 400。
一次性旧源码副本和离线对照测试已清理，观察结果保留在 `offline-old-current.json`。

## 建议与复现命令

现有证据不支持直接回滚排序。优先修复已证实的无效图片输入及历史重放防护，
并补全已脱敏的上游错误码/受控原因展示；随后统一工具历史清理与 Provider 修复契约。
验收应增加合法 JFIF/EXIF 头但缺失 SOF、截断图片和正常 JPEG 对照，验证实际解码。
历史恢复应在构造请求时明确标记不可用图片并保留其他文本、工具结果与思考内容，
避免破坏原始会话记录；新读入的坏图片应返回可操作的工具错误。
不要通过清空全部历史、删除全部 thinking 或反复自动重试来掩盖输入问题。
智谱要求工具调用时返回完整 reasoning，Coding Plan 默认保留历史思考；这也支持
谨慎处理历史，而不是无条件删除。[智谱官方说明](https://docs.bigmodel.cn/cn/guide/capabilities/thinking-mode)
